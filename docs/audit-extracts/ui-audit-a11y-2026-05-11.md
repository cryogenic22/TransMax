# TransMax Frontend — WCAG 2.2 AA Accessibility Audit

**Auditor:** Claude (Opus 4.7, 1M context, read-only audit)
**Date:** 2026-05-11
**Scope:** `frontend/app/workspace/*` + `frontend/components/ui/*` + `frontend/components/control_views/*` + `frontend/components/{WorkspaceShell,Sidebar,TopNavigation}.tsx`
**Bar:** WCAG 2.2 AA. Section 508 / EN 301 549 ride on top.

---

## Summary

- **The shared components (`StatusLifecycle`, `RevisionIndicator`, `ActivityFeed`, `AgentLanes`) are in reasonable shape** — the TMX-3702-a11y sweep landed proper `role="status"`/`role="region"` patterns and dynamic aria-labels. Don't re-flag those.
- **The page-level surfaces (`upload`, `documents/[id]`, `control`) are where the gaps live.** Custom-rolled inline-style markup bypasses the design system, ships no focus indicators, skips heading levels, and uses unlabelled icon-only buttons.
- **The two modals on this audit (delete-confirm in `JobsView`, correction submit in `tools`) have NO accessibility scaffolding** — no `role="dialog"`, no `aria-modal`, no focus trap, no Escape handler, no return-focus. This is a P0 blocker for keyboard-only and screen-reader users and a Section 508 hard fail.
- **Tab semantics are missing across all three tab implementations** (Control Tower, Jobs detail Mode tabs, Document Review view-mode tabs). Native `<button>`s but no `role="tablist"`/`aria-selected` — screen reader users get a flat list of buttons with no group context.
- **Form labelling is sparse to absent** — search box in `JobsView`, glossary `<select>` in `upload`, in-place segment edit textarea in `documents/[id]`, and most LanguageSelector triggers all lack accessible names.

## P0 findings (legal/regulator blockers)

### P0-1. Modals are not modals — `JobsView` delete dialog
**WCAG:** 2.1.2 (No Keyboard Trap, inverse), 4.1.2 (Name/Role/Value), 2.4.3 (Focus Order), 2.4.11 (Focus Not Obscured).
**File:** `frontend/components/control_views/JobsView.tsx:359-395`
**What's wrong:**
- Wrapper div has no `role="dialog"` / `aria-modal="true"`, no `aria-labelledby` pointing at the heading.
- No focus trap: Tab moves through everything **behind** the backdrop, including the still-clickable table rows. A keyboard user can Tab to a hidden trash icon and trigger a second delete on a different row while a delete confirmation is open.
- No Escape handler — Escape does nothing. Users have to mouse over to the X button.
- No initial focus management — focus stays on the original trash button; screen readers don't know the dialog appeared.
- Focus is not returned to the trigger button when the dialog closes.
**What to do:** Add `role="dialog" aria-modal="true" aria-labelledby="delete-heading"`. Add a useEffect that focuses the close (X) button on open, traps focus inside the dialog (Tab/Shift+Tab cycle within), listens for Escape to close, and returns focus to the trigger on close. Easiest: pull in `@radix-ui/react-dialog` (already a likely dependency given Tailwind/Radix patterns elsewhere) and wrap.
**Size:** M.

### P0-2. Same defect — `tools` correction submission modal
**WCAG:** 2.1.2, 4.1.2, 2.4.3.
**File:** `frontend/app/workspace/tools/page.tsx:234-272`
**What's wrong:** Identical to P0-1. Backdrop has `bg-black/50 backdrop-blur-sm` but no `role="dialog"`, no Escape, no focus trap, no return-focus. The textarea has `autoFocus` so initial focus works incidentally, but a keyboard user cannot exit without mouse-clicking Cancel.
**What to do:** Same remediation as P0-1.
**Size:** M.

### P0-3. Same defect — `upload` estimate confirmation dialog
**WCAG:** 2.1.2, 4.1.2, 1.3.1 (Info and Relationships).
**File:** `frontend/app/workspace/upload/page.tsx:901-984`
**What's wrong:** Modal rendered via inline-styled div fixed-overlay. No role, no aria-modal, no focus trap, no Escape, no initial focus. Heading "Translation Estimate" (line 920) is a raw `<h3>` with no programmatic link to the dialog. The Cancel/Start Translation buttons are reachable only after tabbing past everything beneath.
**What to do:** Wrap in a real dialog primitive (radix or your own with the trap). At minimum: `role="dialog" aria-modal="true" aria-labelledby="estimate-heading"`, Escape closes, focus the Cancel button on mount, restore focus to the Translate button on close.
**Size:** M.

### P0-4. Drag-and-drop upload region has no keyboard-only entry-point announcement
**WCAG:** 4.1.2, 1.1.1 (Non-text Content), 1.3.1.
**File:** `frontend/app/workspace/upload/page.tsx:449-531`
**What's wrong:** The drop zone is a `<div>` with cursor:pointer styling, an absolutely-positioned invisible `<input type="file">` (opacity 0) overlaid on top. Tab focus reaches the input but there is:
- No `aria-label` on the input — screen readers announce nothing meaningful.
- No visible focus indicator on the drop zone itself when the underlying input is focused.
- No fallback "click to browse" button as a discrete focusable target. The visible "or click to browse your files" text (line 515) is just decorative text.
**What to do:** Add `aria-label="Upload document for translation (PDF, DOCX, TXT)"` to the input. Add a `:focus-within` style on the drop zone container so a keyboard user sees focus. Better: render an explicit `<button>Browse files</button>` next to the drop instruction, triggering the input via ref.
**Size:** S.

## P1 findings (real user-blocking a11y gaps)

### P1-1. Tabs are unlabelled buttons — Control Tower
**WCAG:** 1.3.1, 4.1.2.
**File:** `frontend/app/workspace/control/page.tsx:42-75`
**What's wrong:** Four `<button>`s used as a tab strip. No `role="tablist"` on the container, no `role="tab"` per button, no `aria-selected={currentTab === 'overview'}`, no `aria-controls` linking to the panel div. Screen reader users hear "Overview, button. Jobs, button. Compliance & Audit, button." with no indication that they form a group or which one is active.
**What to do:** Apply WAI-ARIA Tabs pattern: `role="tablist"` on the wrapper div, `role="tab"` on each button, `aria-selected={...}`, `aria-controls={panelId}`, and matching `role="tabpanel"`/`aria-labelledby` on the rendered view component below. Add arrow-key navigation between tabs (LEFT/RIGHT) per the pattern.
**Size:** S.

### P1-2. Same defect — Job detail Mode tabs
**WCAG:** 1.3.1, 4.1.2.
**File:** `frontend/app/workspace/jobs/[id]/page.tsx:185-209`
**What's wrong:** Overview/Translate/Review tabs. Same missing semantics as P1-1. Active tab is conveyed visually only (border colour).
**What to do:** Same as P1-1.
**Size:** S.

### P1-3. Same defect — Document review view-mode tabs
**WCAG:** 1.3.1, 4.1.2, 2.5.5 (Target Size — partial).
**File:** `frontend/app/workspace/documents/[id]/page.tsx:286-319`
**What's wrong:** Scorecard/Segments/Preview tabs. Same missing tablist semantics. Also no `aria-current` fallback.
**What to do:** Same as P1-1.
**Size:** S.

### P1-4. Heading hierarchy skips levels in `documents/[id]`
**WCAG:** 1.3.1, 2.4.6 (Headings and Labels).
**File:** `frontend/app/workspace/documents/[id]/page.tsx:275, 510, 571, 881`
**What's wrong:** Page `<h1>` is the document name. The next headings are `<h3>` ("Quality Categories", "Issues Requiring Review") with no intervening `<h2>` — screen readers reading the document outline see h1 → h3 with a gap. Preview view (line 881) re-uses `<h1>` for the document name inside main content, producing two h1s on the same page.
**What to do:** Promote "Quality Categories" and "Issues Requiring Review" to `<h2>`. Demote the Preview view's `<h1>` to `<h2>` (or wrap with a region landmark).
**Size:** XS.

### P1-5. Sidebar accordion triggers use `role="button"` without keyboard handler
**WCAG:** 2.1.1 (Keyboard).
**File:** `frontend/components/Sidebar.tsx:78-90, 172-187`
**What's wrong:** Two `<div role="button" tabIndex={0}>` elements that toggle accordion sections. They have `onClick` but no `onKeyDown` to handle Enter/Space — keyboard users can focus them but not activate. Sighted users with motor impairments who navigate by keyboard are blocked from expanding "Control Tower" or "Recent Documents".
**What to do:** Replace with `<button type="button">` (preferred — gets keyboard activation, focus styling, and the right role for free) or add `onKeyDown` handling `Enter` and `Space` (preventing default to avoid scrolling). Same fix in `QualityDashboard.tsx:114-118` (`role="button"` div with no tabIndex and no keyboard handler).
**Size:** S.

### P1-6. Sidebar nav has no landmark or aria-current
**WCAG:** 1.3.6 (Identify Purpose — AA in 2.2), 4.1.2.
**File:** `frontend/components/Sidebar.tsx:43-225`
**What's wrong:** `<aside>` wrapper is fine, but `<nav>` (line 55) has no `aria-label`. There are TWO `<nav>`s on the page (top + sidebar) — assistive tech can't tell them apart. Active links don't carry `aria-current="page"` — only a CSS class. Screen reader users navigating links get no indication of which is current.
**What to do:** Add `aria-label="Workspace"` to the sidebar `<nav>` and `aria-label="Primary"` to TopNavigation's `<nav>` (line 102 of `TopNavigation.tsx`). Add `aria-current={isActive(item.href) ? "page" : undefined}` to each `<Link>` in both files.
**Size:** XS.

### P1-7. Search box in `JobsView` has no label
**WCAG:** 1.3.1, 3.3.2 (Labels or Instructions), 4.1.2.
**File:** `frontend/components/control_views/JobsView.tsx:180-186`
**What's wrong:** `<input type="text" placeholder="Search jobs...">` with placeholder only. Placeholders disappear on input and have insufficient contrast. Screen readers may or may not announce the placeholder as the accessible name.
**What to do:** Add `aria-label="Search jobs by name or language"` (or visible label `<label className="sr-only">`).
**Size:** XS.

### P1-8. Sidebar's free-text "Search documents..." input is functionless and unlabelled
**WCAG:** 4.1.2, 3.3.2.
**File:** `frontend/components/Sidebar.tsx:47-52`
**What's wrong:** Placeholder-only input with no onChange handler. It is decorative dead weight. A screen reader user will tab into it expecting it to filter.
**What to do:** Either wire it up to a search route OR remove it. If kept temporarily, add `aria-label="Search documents"` and `disabled` so the keyboard user is told it's not actionable.
**Size:** XS.

### P1-9. Glossary `<select>` in upload page is unlabelled
**WCAG:** 1.3.1, 3.3.2, 4.1.2.
**File:** `frontend/app/workspace/upload/page.tsx:624-647`
**What's wrong:** `<select>` is preceded by a `<div>` text "Glossary (optional)" but they're not programmatically linked — no `<label htmlFor>`, no `aria-labelledby`. Screen readers announce "combobox, None" with no context.
**What to do:** Add `id="glossary-select"` to the `<select>` and convert the text div into `<label htmlFor="glossary-select">Glossary (optional)</label>`.
**Size:** XS.

### P1-10. Segment-edit textarea has no accessible name
**WCAG:** 1.3.1, 3.3.2, 4.1.2.
**File:** `frontend/app/workspace/documents/[id]/page.tsx:717-731`
**What's wrong:** The translated-text edit textarea has no label. Screen readers say "edit, multi-line, [edit text content]". A reviewer making HITL corrections (audit-chain critical per A1) has no announced context for which segment they're editing.
**What to do:** Add `aria-label={`Edit translation for segment ${idx + 1} of ${segments.length}`}` to the textarea. Bonus: announce save success/failure with an `aria-live="polite"` region.
**Size:** XS.

### P1-11. Icon-only buttons lack accessible names — multiple sites
**WCAG:** 1.1.1, 4.1.2.
**Files:**
- `frontend/components/control_views/JobsView.tsx:271-296` (Download icon button), `:298-304` (Trash icon button), `:199-201` (Refresh icon button) — only `title` attributes, which are not reliable screen-reader names and absent on touch.
- `frontend/app/workspace/upload/page.tsx:365-390` (Swap-languages button — only `title`), `:411-419` (X close-error button — no name at all), `:579-591` (X remove-file — only `title`).
- `frontend/components/TopNavigation.tsx:172-187` (Bell notifications button — no name, no title).
- `frontend/components/ui/CopyButton.tsx:24-42` — only `title="Copy to clipboard"`.
- `frontend/components/ui/RichTextEditor.tsx:22-67` — every toolbar button has only `title=` (Bold/Italic/Bullet List/etc.).
**What to do:** Replace `title` with `aria-label`. Keep `title` as well if you want the tooltip on hover, but `aria-label` is the load-bearing one. Bell button needs `aria-label="Notifications"`.
**Size:** S overall (many small edits).

### P1-12. Toast notifications: confirm Sonner is configured for screen readers
**WCAG:** 4.1.3 (Status Messages).
**Files used:** sonner toasts called in `upload/page.tsx`, `tools/page.tsx`, `documents/[id]/page.tsx`, `JobsView.tsx`, `CopyButton.tsx`.
**What's wrong:** Sonner defaults to a `role="status" aria-live="polite"` region, but only if the `<Toaster>` is rendered with default settings AND not overridden. I didn't see a `<Toaster>` definition in this audit pass — confirm it exists in the root layout and is not configured `richColors` / `theme` only without preserving the live-region semantics. A regulator-facing audit-event toast that doesn't announce is a silent failure.
**What to do:** Verify `<Toaster richColors closeButton position="top-right" />` or similar in the root `app/layout.tsx`. Add an explicit smoke test that toasts emit announcements.
**Size:** XS (verify) — S if `<Toaster>` is missing or misconfigured.

### P1-13. `loading="..."` and `aria-busy` missing on long-polling sections
**WCAG:** 4.1.3.
**Files:**
- `frontend/app/workspace/upload/page.tsx:681-742` (Translating state) — `<Loader2>` icon spins but no `aria-busy` on the wrapper, no `role="status"` announcement.
- `frontend/app/workspace/documents/[id]/page.tsx:193-208` (Loading document) — `<Loader2>` with "Loading document..." text but no `role="status"` or `aria-live`.
- `frontend/components/control_views/JobsView.tsx:159` ("Loading jobs...") — same.
**What to do:** Wrap each loader in `<div role="status" aria-live="polite" aria-busy="true">` so SR users hear "Loading document". For the upload pipeline, also announce step transitions ("Validating document, in progress" → "Translating, in progress") via aria-live updates on the LiveIsland.
**Size:** S.

### P1-14. Progress bars convey state only via colour + width
**WCAG:** 1.1.1, 1.3.1, 4.1.2.
**Files:**
- `frontend/app/workspace/upload/page.tsx:703-722` (translation progress).
- `frontend/components/control_views/JobsView.tsx:249-257` (job-row progress).
- `frontend/app/workspace/documents/[id]/page.tsx:523-530` (per-category quality bars).
- `frontend/app/workspace/documents/[id]/page.tsx:786-810` (per-segment confidence).
**What's wrong:** All four are styled `<div>`s with no `role="progressbar"`, no `aria-valuenow` / `aria-valuemin` / `aria-valuemax`. Screen reader users get no progress information beyond whatever text label sits next to it.
**What to do:** Wrap each bar div with `role="progressbar" aria-valuenow={pct} aria-valuemin={0} aria-valuemax={100} aria-label="Translation progress"`. Visible adjacent text (e.g. "85%") is fine to keep but the role is the audit hook for assistive tech.
**Size:** S.

### P1-15. ConfidenceMeter tooltip is mouse-only
**WCAG:** 1.4.13 (Content on Hover or Focus), 2.1.1.
**File:** `frontend/components/ui/ConfidenceMeter.tsx:30-86`
**What's wrong:** The "Score Breakdown" tooltip surfaces via `group-hover:opacity-100`. There's no `group-focus-within:opacity-100`, no keyboard equivalent. The wrapper is a `<div>` with `cursor-help` but no `tabIndex`. Keyboard and touch-only users cannot see the breakdown that explains a 78% trust score — which is the regulator-facing rationale.
**What to do:** Change the outer wrapper to `<button type="button">` (or add `tabIndex={0}`), add `group-focus-within:opacity-100` to the tooltip's class list, and ensure tooltip content has `role="tooltip"` and is referenced by `aria-describedby` on the trigger. Per WCAG 1.4.13, the tooltip must also be dismissible (Escape) without moving pointer.
**Size:** S.

## P2 findings (polish)

### P2-1. Touch targets below 24×24 / 44×44 (2.2)
**WCAG:** 2.5.8 (Target Size Minimum — new in 2.2, requires 24×24 CSS px).
**Files:**
- `frontend/components/control_views/JobsView.tsx:271-304` — Download & Trash icon buttons are bare 16px icons with no padding wrapper. Hit-target collapses to ~16×16, well under 24×24. AAA bar is 44×44; we're failing AA at 24×24.
- `frontend/app/workspace/upload/page.tsx:411-419` (X close-error button), `:579-591` (X remove-file button) — `padding: 4px` around an 18-20px icon ≈ 26-28px, just over the line but tight.
- `frontend/components/ui/RichTextEditor.tsx` toolbar — `p-1.5` (6px) + 16px icon ≈ 28×28, OK at AA.
**What to do:** Add `p-2` (or inline padding `0.5rem`) to the JobsView icon buttons. Add a minimum hit-target wrapper class for icon-only buttons across the app.
**Size:** XS.

### P2-2. Colour-only meaning for status states
**WCAG:** 1.4.1 (Use of Color), 1.3.1.
**Files:**
- `frontend/app/workspace/documents/[id]/page.tsx:782-810` (segment confidence) — green vs amber bar is the only signal of "high vs medium confidence". Adjacent percentage is provided (good), but the bar fill colour alone carries category meaning.
- `frontend/app/workspace/documents/[id]/page.tsx:185-191` (`getSeverityColor`) — severity is conveyed via bg/border/text colour AND an icon, which is good. Sample passes.
- `frontend/components/Sidebar.tsx:203` (`.sidebar-status-dot`) — pure-colour dots indicating recent doc status. Hover/title shows nothing.
**What to do:** Confidence bar — already paired with `%` text so passes. The sidebar status dot should have `title` and `aria-label` showing the status string.
**Size:** XS.

### P2-3. Disabled state contrast on the language-swap button
**WCAG:** 1.4.11 (Non-text Contrast).
**File:** `frontend/app/workspace/upload/page.tsx:373-390`
**What's wrong:** When `sourceLanguage === "auto"` the button colour is `#ccc` on white. The border is `#dadce0` on white. Both well under 3:1 contrast for UI components (1.4.11 AA). Disabled controls are exempt from contrast, but they MUST still be discernible; here they border-blend.
**What to do:** Use `#9aa0a6` (Material's "disabled foreground") or darken to `#80868b` so the icon is visibly present, while keeping the cursor:not-allowed semantic.
**Size:** XS.

### P2-4. Placeholder text contrast on amber alerts
**WCAG:** 1.4.3 (Contrast Minimum).
**File:** `frontend/app/workspace/upload/page.tsx:428-446`
**What's wrong:** Amber-800 (#92400e) on amber-50 (#fef3c7) measures ~7.5:1 — passes. But the "(Optional) Compare with Original Source" divider text in `tools/page.tsx:447` is `#aaa` on white = 2.85:1 — fails 4.5:1 normal-text minimum. The "or click to browse" subtitle in upload (#5f6368 on white, line 514) ≈ 5.7:1 — passes. The "Selected: fr, de, …" line in `tools/page.tsx:547` is `text-slate-400` ≈ 3.5:1 — fails.
**What to do:** Darken `#aaa` divider text to `#6b7280` (slate-500). Use `text-slate-500` instead of `text-slate-400` for informational text on white. Audit all `text-slate-400` usages site-wide.
**Size:** S.

### P2-5. Empty `<div style={{ width: "160px" }} />` spacer creates a focusable gap... actually no
**WCAG:** N/A (this one's a non-issue on inspection — it's a layout spacer with no focusable content). Not flagged.

### P2-6. `<time dateTime>` is used in some places but bare text dates elsewhere
**WCAG:** 1.3.1.
**Files:** `frontend/components/ui/ActivityFeed.tsx:110` correctly uses `<time dateTime={...}>`. `JobsView.tsx:265-267` and `documents/[id]/page.tsx` use bare formatted dates in `<td>` cells.
**What to do:** Wrap formatted dates in `<time dateTime={iso}>display</time>` so assistive tech and date-extraction tools can parse them. Cheap consistency win.
**Size:** XS.

### P2-7. The `<table>` in `JobsView` has no caption
**WCAG:** 1.3.1.
**File:** `frontend/components/control_views/JobsView.tsx:216-313`
**What's wrong:** Data table for jobs has thead/tbody/th but no `<caption>` or `aria-label`. Screen readers announce "table with 7 columns and N rows" — no name.
**What to do:** Add `<caption className="sr-only">Translation jobs</caption>` as the first child of `<table>`, or `aria-label="Translation jobs"` on the `<table>` itself.
**Size:** XS.

### P2-8. RichTextEditor toolbar buttons missing `aria-pressed`
**WCAG:** 4.1.2.
**File:** `frontend/components/ui/RichTextEditor.tsx:22-67`
**What's wrong:** Toggle buttons (Bold/Italic/Bullet List) visually convey active state via background colour. They need `aria-pressed={editor.isActive('bold')}` so screen readers know it's a toggle button and which state it's in.
**What to do:** Add `aria-pressed={editor.isActive('bold')}` (etc.) to each toggle, and `aria-label="Toggle bold"` to give it an explicit name beyond `title`.
**Size:** XS.
