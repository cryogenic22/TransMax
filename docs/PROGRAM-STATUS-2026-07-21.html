The engine is real. Almost none of it is switched on.

TransMax has built a defensibility core with genuine regulatory substance — a chained, independently re-computable audit ledger with Merkle day-anchors; a pure MQM 2.0 scoring engine with versioned content-type profiles; an independent judge with planted-defect recall, Cohen's κ and a CI reliability gate; prompt-version pinning; an eval harness; a ratchet. That work is good and it is the moat.

It is also, in fifteen separate places, wired to nothing.

The program's failure mode is not incompleteness — it is disconnection. The MQM engine's cutover flag mqm_engine_enabled is declared at config.py:113 and read by zero lines of application code. The audit-chain UI component exists and is imported by nothing. The MCP server exposes six tools and is imported by nothing. The strongest asset in the product is invisible to every user who might be persuaded by it.

The maturity vocabulary used throughout this report

Percentages are the vacuous-green hazard in miniature, so this report does not use them. Every capability below is placed in one of four states, each backed by a file reference you can check.

Live

In the default production path today, changing real outcomes.

Partial

Genuinely there, but one layer of several, or missing a dimension the vision requires.

Dark

Built, tested, merged — and behind a default-off flag or with zero callers. Cost paid, value not collected.

Absent

Not in the code. Verified by repo-wide search, not assumed.

§2

Architecture, measured against the target stack

Six layers, from the callers down to the governance plane. Each row states what exists in app/ today and what the layer is missing.

CallersPartial

12 REST routers. Upload a document, translate a document, download a document, patch a segment, verify a chain, export an audit bundle.

Missing: any component- or delta-shaped entry point. There is no “here are three changed statements, tell me what you already have” call. The MCP server exists but is imported nowhere and absent from .mcp.json. webhook_url is accepted in the v1 schema and never fired.

Agent layerAbsent

—

Missing entirely: the tool router, policy guard, idempotency keys and callback dispatch that would let an autonomy boundary live in the API rather than in the caller's goodwill. Today RBAC guards routes; nothing refuses an action because it would bypass a review gate.

WorkflowPartial

A LangGraph pipeline with real state transitions, a budget guard, a drift gate that forces human review, and a stuck-job sweeper.

Missing: durable execution — queue_service.py is a 32-line wrapper over FastAPI BackgroundTasks, so jobs die with the process. No SLA clock, no pathway concept (standard / urgent-safety / linguistic), no vendor routing, and the sweeper is default-off.

IntelligenceLive

Terminology-constrained LLM drafting through a versioned prompt registry with content hashes; per-call token and cost telemetry into the audit chain; back-translation with a semantic-drift gate that escalates to human review; a prompt-injection gate on source text.

Missing: alignment and memory mining (no way to warm-start an estate from a customer's existing translations), and the model router is off, so the “ensemble” is one model sampled twice — self-consistency, not independence.

Deterministic corePartial

Stable UUID segments with element metadata and gate results. Exact-match TM binding that genuinely bypasses the LLM. Forbidden and strict glossary terms enforced as hard CRITICAL defects that set a segment to BLOCKED — enforcement is real, not advisory.

Missing: the reuse layer that makes the economics work. Segments are cascade-deleted children of a document; a repo-wide search for component, statement or cross-language identity returns zero matches. Fuzzy matching is not in the production path and returns a hardcoded score. QRD exists only as heading strings — there is no identifier-bound standard text that never reaches MT. Termbases are one flat list, not the layered MedDRA / EDQM / QRD / product stack the knowledge ADR specifies.

Governance planePartial

A domain-separated chained-hash ledger (v2) with an independently re-implemented verifier — two implementations agreeing is the spec check — plus a tenant-scoped verification API, Merkle day-anchor builder with S3 Object Lock fields, tenant scoping, RBAC on every privileged route, and structured auth-event auditing.

Missing: e-signature. A repo-wide search for signer identity, meaning-of-signature or Part 11 signing returns one aspirational docstring and no implementation; approval is a bare status flip and there is no lock state at all. The v2 chain also cannot hold system events — job_id is NOT NULL, so a glossary edit, a role change or a flag flip has nowhere chained to go.

§5

Reading the Concord vision against our own

The headline finding is that Concord is not a competing roadmap — most of it is a restatement of doctrine we have already written down, sometimes in more depth than the vision document itself reaches. Its value is concentrated in one structural idea and a handful of presentational ones.

Concord is a demand-side vision: statements, reuse, cost per changed statement, a service that is called rather than visited. Ours has been a supply-side vision: evidence, judges, ledgers, calibration. We have been building the thing that makes the promise defensible while the promise itself stayed abstract. The two meet at exactly one place in the code — segment identity.

Confirms — no new work

  • Deterministic floor before stochastic judges. Already our A2 plus the no-vacuous-green principle.
  • Terminology as constraint, not suggestion. Our knowledge ADR is finer: four enforcement levels (suggested / preferred / required / locked) against Concord's binary.
  • Layered termbases. Already specified as a five-store asset map with precedence, plus a nomenclature graph with effective-dating that Concord has no equivalent for.
  • GAMP 5 posture, model change control, ALCOA+, human accountability. All already written into A1/A6/A8 and the regulatory pack.
  • MCP deferred to a later phase — its own roadmap places the agent at months 6–12, matching our v3.1 deferral.

Adds — genuinely new

  • The component translation graph. Statements as first-class nodes, translations bound to them, multilingual state queryable, approved text locking back as a reusable asset. We have zero code for this.
  • Delta-only intake. Submit changed components, get bound results. Follows directly from the graph and inverts our document-upload API shape.
  • Reuse economics as the product metric — cost per changed statement, reuse rate. Our metrics are all quality and cycle time; none is economic.
  • Legacy estate onboarding — alignment plus memory mining, so a pilot starts warm. Without it reuse begins at zero and the entire economic story fails on day one.
  • Standard text bound by identifier, never sent to MT, never editable. Ours is heading strings for validation only.
  • Refusal as a product surface. Demonstrating the system declining an unsafe action is the most persuasive thing a regulated buyer can watch. We fail loud everywhere and surface it nowhere.
  • A provenance vocabulary for the UI — bound / constrained / AI-assist / AI-built / human, each carrying its own rule. We have the audit data and no language for it.
  • Two lifecycle states we lack: leveraged (delta isolated) and locked (assets written back).

Reject or reframe

  • A scalar QE score driving routing. Weaker than what we already have and it reintroduces vacuous green through the back door. Derive a QE-style band from the MQM score for display; keep the span-level annotation as the record. Do not adopt a second quality instrument.
  • Reuse rate above 85% as a headline. Dangerous unless binding revalidates. An exact match bound without re-running the deterministic checks propagates a stale error at scale under an audit line that reads “bound”. Our rule should be stricter than the source document's: TM entries carry the termbase and profile version they were approved under, and binding still runs the cheap deterministic gates even though it skips the model.
  • Embedded-first. The right end state, the wrong starting point — our pilot buyers have no labelling platform to call from. Stay hub-first, but shape the API around components now so embedded mode is later a thin adapter rather than a rewrite.
  • A separate SDK quality path. Adopt the external pack's harder rule instead: no surface may be weaker than the engine. That retires our SDK fork rather than blessing it.

Where we are already ahead

  • Concord says “immutable audit trail”. We have a domain-separated hash chain, an independently re-implemented verifier, day-level Merkle anchors and a verification API.
  • Concord says “QE calibration reviewed quarterly”. We have planted-defect recall, precision floors, Cohen's κ and a CI gate that fails the build on drift.
  • Concord's termbase layering versus our five-store asset map with enforcement levels, a nomenclature graph, effective-dating and a strictly-negative Black Book.
  • Prompt-version pinning with content hashes; a ratchet that only tightens; a golden eval corpus.

These are the things to protect in any replan — and the things to put on a screen, because right now a buyer cannot see any of them.

The strategic consequence Revised

The component graph is the highest-value idea in the Concord material — and TransMax should not build it. reSCApe already owns it, in shipped code. See §8, which supersedes the conclusion originally drawn here.

What survives from this section is the sequencing constraint: segments today are cascade-deleted children of a document, and the unreconciled split between the graph's string Document and the ledger's UUID TranslationJob must be settled before anything binds to it. That still makes TMX-3221 the gateway ticket — but its target changes. The canonical job aggregate must be designed to carry a foreign component reference, so it is done once.

Seven rules to close it down

  1. One ID namespace, uniqueness enforced. Extend the drift auditor to fail on a duplicate or unregistered ID. A ticket mentioned in prose without a row is a lint error, not a plan.
  2. Five states, no more. READY · WIP · BLOCKED · DONE · DROPPED. “Done pending push” is not Done — CLAUDE.md already says so; make the vocabulary make it impossible to write.
  3. Spawn triage within one batch. Every follow-up gets promoted, parked or dropped before the next batch closes. Default is drop. The anti-bloat gate applies to tickets exactly as it applies to code.
  4. One epic axis. Vision E1–E14 is canonical; the v3 E1–E11 set is substrate folded underneath it; WS0–WS10 is a lens for the scorecard and never a roadmap. Publish the map once, then stop cross-referencing.
  5. Commit the strategy. ADR-0008, the external pack and the scorecard YAML are untracked. The ADR designates the scorecard a tracked release-gate artifact; it is not tracked. This is a Tier-0 entropy hit against A10.
  6. One release gate. The scorecard is the only readiness signal. Retire story-point-weighted percentage dashboards — an estimate rendered as a progress bar is a vacuous-green vector by construction.
  7. Regenerate, don't maintain. The board should be derived from worksheet headers and git, the way the drift auditor already reads them. Hand-maintained state is what produced the four self-contradictions.

reSCApe changes the answer

The component translation graph — the one idea §5 identified as genuinely new and worth building — is already built, in the other repo. reSCApe owns component identity, versioning, effective dating, lineage, markets, label scope and, it turns out, a working Part 11 signature service. TransMax must not build a second one of any of them.

The two products are not peers. reSCApe is the product: it owns what a statement is, which version is effective, which markets carry it and who signed it. TransMax is the engine: given a statement version and a target locale, it produces a translation with a quality adjudication, a provenance record and a verifiable audit entry. One owns the content graph; the other owns the language layer. Neither should own both.

The integration already exists, and it is the worst kind

TransMax is vendored into reSCApe as a git submodule pinned to 3 March 2026 New

.gitmodules points packages/transmax at the TransMax GitHub repo, pinned at 274557a — the second commit in TransMax's entire history. Every piece of defensibility work since then is absent from what reSCApe actually runs: no audit ledger v2, no verifier, no Merkle anchors, no MQM engine, no multi-tenancy, no prompt registry, no injection or budget guard, no drift gate. reSCApe offers a "transmax" provider tier whose pharma-grade quality checks come from a pre-moat snapshot.

Who owns what

A vendored module can live in-process. A regulated engine with its own audit ledger, tenancy and validation evidence cannot — if TransMax runs inside reSCApe, no one can answer whose chain recorded the translation. That is the structural reason this must be a service, not a package.

The cleanest fact in the whole analysis

reSCApe's component model is monolingual. There is no language or locale column on components or component_versions — one language column exists in twenty-three migrations and it belongs to carton-label specs. The variant selector branches on market only. DerivationType.TRANSLATED_FROM and LOCALIZED_FROM are declared in the enum and written by nothing. reSCApe's own draft architecture note concedes the workaround in writing: locale is routed through market_scope_markets “until a dedicated language field exists on Component”.

This makes the boundary unusually clean. TransMax is not duplicating reSCApe and never was — it supplies the dimension reSCApe does not have. The two systems are orthogonal: reSCApe indexes content by market, TransMax by locale, and the join is a component version.

It also names the one blocking prerequisite. Because assembly, the build hash, label sets, approval and signature all operate on Components, a translated label must become a component version in reSCApe, or none of that machinery applies to translations and we would rebuild all of it. That requires a locale column on the component model, in the variant selector, and in the build hash — currently a French and an English label are indistinguishable to build_hash. Under reSCApe's Backend Lock that is an RFC, and it is the first thing to file.

Two smaller findings that cut in our favour. reSCApe's translation subsystem is a prototype, not a rival: an in-memory job dict that dies on restart, ten hardcoded languages, and zero references to component_id anywhere in its routes — so there is very little to retire and nothing to build on. And reSCApe's audit_log is not a chained ledger — no prev_hash, no sequence; rows are individually fingerprinted but unlinked, so deleting or reordering one is undetectable. TransMax's ledger is therefore not a duplicate capability. It is the evidence plane the portfolio does not otherwise have.

The seam

Not a submodule. A versioned HTTP contract with an async job and a callback, keyed on reSCApe's component version. That single foreign reference is the whole “component translation graph” TransMax needs — it never invents statement identity and never diffs documents, because reSCApe already versions components and computes the impact set.

reSCApe has already specified the memory key, and it is better than the one §5 proposed: (source_component_version.hash_canonical, target_locale, termbase_version_id). Keying on the content hash means identical text reuses across components; including termbase_version_id means a terminology change automatically invalidates the match. That is the bind-revalidation hazard §5 warned about, solved in the key rather than in a policy someone has to remember. Adopt it verbatim.

The good news: most of this contract already exists. app/schemas/api_v1.py has an idempotency key, a governance profile (archetype / risk tier / modality / regulatory profile) and a webhook field, and the v1 routes already expose result, audit-bundle and certificate endpoints. What is missing is a source reference block on the request, a disposition + MQM + provenance block on the response, a webhook that actually fires, and a durable execution path.

One rule both repos need

Four instances of a single disease turned up across the two codebases: last_derived_at advanced without re-deriving; mode: "transmax_ai" reported over a heuristic fallback; a fabricated compliance posture panel; an SDK emitting [target] source labelled MT. reSCApe already wrote the cure for its own AICAT taxonomy — adopt the vocabulary, derive the value, never store the string. Generalise it:

Rule A provenance or compliance claim must be derived from the artefact that produced it — a prompt hash, a chain entry, a signature record, a live posture read. Never stored as a string, never asserted by a default, never survived from a fallback path.
