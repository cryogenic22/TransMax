## 3. Design

### Why a mixin + event listener (vs. per-model columns)

I considered three alternatives:

1. **Per-model columns + per-model `delete()` overrides** — most explicit but 23× duplication. Rejected: A drift risk every time a new model is added (will the dev remember to add the columns? to override delete?).

2. **Mixin + class-level `before_delete` listener** — chosen. The mixin carries the columns and the `soft_delete()` method. A SQLAlchemy `event.listens_for(SoftDeleteMixin, 'before_delete', propagate=True)` raises on hard-delete. New models get all three behaviours by inheriting the mixin. **Trade-off**: mixin must be inherited, not just imported as a column list — but that's standard SQLAlchemy practice.

3. **Session-level `delete()` interceptor on the global session factory** — less explicit than (2) and entangles with TMX-3012's session-factory work. Rejected.

### Auto-filter strategy

SQLAlchemy 2.x supports `with_loader_criteria()` registered as a session-wide event handler. Every `session.query()` against a model with the mixin gets `AND is_deleted = false` appended automatically.

```python
@event.listens_for(Session, 'do_orm_execute')
def _add_soft_delete_filter(execute_state):
    if execute_state.is_select and not execute_state.execution_options.get("include_deleted", False):
        execute_state.statement = execute_state.statement.options(
            with_loader_criteria(SoftDeleteMixin, lambda cls: cls.is_deleted == False, include_aliases=True)
        )
```

To bypass for forensic / admin queries: `session.query(Document).execution_options(include_deleted=True).filter(...)`.

### Why no FK on `deleted_by`

The actor that deletes a row may be a system actor (e.g., scheduled-cleanup job, migration script) without a corresponding `users` row. A FK would force every system action to materialise a "system user," which is more bookkeeping than value. Instead, `deleted_by` is informational `VARCHAR(36)` — usually a UUID matching `users.id`, but free-form for system actors. This matches the convention in `app/models/database.py:DeletionRecord.deleted_by`.

### Migration order vs. TMX-3011

The migration runs after `b2f3011_org_fk`. It uses the same defensive introspection — adds columns only where the table exists, idempotent re-runs.

### `DeletionRecord` coexistence

`DeletionRecord` (in `database.py`) is a forensic snapshot table that captures point-in-time metadata when a Document is deleted (name, segment count, who, when, why). It exists for forensic queries: "what did this row look like when it was deleted?"

Soft-delete columns are different: they're the live status flag on the actual row. Both live together: when `Document.soft_delete()` is called, it sets the flag AND a `DeletionRecord` is written by the API endpoint code (existing flow).

## 6. Red team

Walked the Tier 2 22-item checklist + A1-A10 against the diff.

**Findings I deliberated**:

1. **`do_orm_execute` event listener is global.** It applies to every Session created via SessionLocal AND every Session bound to the engine. If a test creates its own Session via `sessionmaker(bind=engine)`, it inherits the listener (because `event.listens_for(Session, ...)` is class-level). Verified by the test fixture which creates a new Session and observes the filter active. **No leak.**

2. **The mixin's `before_delete` is registered with `propagate=True`.** This is essential — without it, subclasses don't inherit the listener. Verified by the hard-delete-refusal test on `Document`, which is `class Document(SoftDeleteMixin, Base)`. **Correct.**

3. **`with_loader_criteria(SoftDeleteMixin, ...)` filters by class hierarchy.** Models that DON'T inherit the mixin (e.g., `LanguagePack`) are unaffected. Verified by `test_language_packs_does_not_have_soft_delete`. **Correct.**

4. **`include_deleted=True` opt-in is for forensics + admin only.** The current codebase has no consumer yet; TMX-3017 audit-trail forensic queries will use it. **Tracked**: when `app/services/evidence_service.py` (audit forensic queries) lands, it must use `include_deleted=True` to surface the full history.

5. **Unique constraints + soft-delete interaction.** A unique constraint on (e.g.) `User.email` will prevent re-creating a deleted user with the same email. This is a known soft-delete tradeoff. Mitigation: when restoring, restore by `UPDATE SET is_deleted=False`; when re-creating, the auto-filter hides the old row but the unique constraint still rejects duplicates at the SQL level. **Acceptable for v3.0**; tracked for TMX-3017 if a customer hits it.

6. **`server_default` for `is_deleted` is the SQL `false`.** Existing rows in dev/prod that pre-date the migration get `FALSE` set by SQL default during ALTER. No backfill UPDATE needed. **Verified** in migration logic.

**Forward-looking flags**:

1. **TMX-3012** (next): the tenant-scoped session factory layers ON TOP of the soft-delete filter. Both `with_loader_criteria` registrations (org + soft-delete) coexist via SQLAlchemy's stacking semantics.
2. **TMX-3017** (rationalisation): when the C-06 unwind ships, the 7 currently-skipped tables (`audit_records`, `chunk_translations`, `quality_reports`, `translation_glossaries`, `translation_jobs`, `translation_memory`, `users`) need their alembic create-table revisions updated to include the soft-delete columns from day 1.
3. **TMX-3105** (e-signature flow): when a reviewer e-signs a document, the signing event must be an audit event AND the `Document` row must transition to a "signed" status — but should NOT be soft-deleted. Soft-delete is a different lifecycle than approval. Spec'd in plan §6.A but worth re-reading when E2 lands.
4. **Forensic queries**: `app/services/evidence_service.py:audit_records = session.query(AuditRecord).all()` (line 44) will silently exclude soft-deleted audit records once 3015 lands. **Important**: this method is for evidence bundles — it MUST surface deleted rows. **Tracked**: evidence_service must use `include_deleted=True`.
