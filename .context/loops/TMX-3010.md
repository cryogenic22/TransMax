## 3. Design

### Where does the table live? (A4)

Per CLAUDE.md A4: *"new tables go in `database.py` (the simpler layer) unless they need pgvector. If you need both, raise it at design review."* The handoff explicitly approves putting `organizations` reachable from both layers. Resolution:

- **Model definition**: `app/models/database.py` (the operational layer, since `organizations` doesn't need pgvector).
- **Primary-key type**: a portable `GUID` TypeDecorator in `app/models/types.py` (NEW file). Resolves to `postgresql.UUID(as_uuid=False)` on Postgres and `CHAR(36)` on SQLite. Stores UUIDs as strings either way (Python-side `str(uuid.uuid4())`).
- **FK strategy** (sets up TMX-3011): `database.py` tables that already use `String(36)` IDs FK to `organizations.id` directly — type-compatible because `GUID` becomes `CHAR(36)` on SQLite. `translation.py` tables that already use `UUID(as_uuid=True)` FK to `organizations.id` — type-compatible on Postgres because `GUID` becomes native `UUID` there. **Trade-off**: in `translation.py`, the existing `organization_id = Column(UUID(as_uuid=True))` columns are bare (no FK). In TMX-3011 I'll switch them to `Column(GUID, ForeignKey("organizations.id"))` — straightforward.

**Alternative considered + rejected**: Two parallel `organizations` tables, one per layer. Rejected: doubles the maintenance, breaks A1 (audit-by-default — which org owns what?), and would make TMX-3017 (model rationalisation) strictly worse.

### Schema

```python
class Organization(Base):
    __tablename__ = "organizations"
    id           = Column(GUID, primary_key=True, default=lambda: str(uuid.uuid4()))
    name         = Column(String(255), nullable=False)
    slug         = Column(String(64), unique=True, nullable=False, index=True)
    org_kind     = Column(String(32), nullable=False, default="customer")  # system|customer|partner
    is_active    = Column(Boolean, nullable=False, default=True)
    metadata_json = Column(JSON, nullable=True)
    created_at   = Column(DateTime, default=lambda: datetime.now(timezone.utc), nullable=False)
    updated_at   = Column(DateTime, default=lambda: datetime.now(timezone.utc),
                          onupdate=lambda: datetime.now(timezone.utc), nullable=False)
    __table_args__ = (
        CheckConstraint("org_kind IN ('system','customer','partner')", name="ck_organizations_org_kind"),
    )
```

### Default-org seed

Per handoff approval:

```sql
INSERT INTO organizations (id, name, slug, org_kind, is_active, created_at, updated_at)
VALUES ('00000000-0000-0000-0000-000000000001', 'default', 'default', 'system', TRUE,
        '2026-05-05T00:00:00+00:00', '2026-05-05T00:00:00+00:00');
```

Done in the migration's `upgrade()` after `op.create_table()`. Idempotent via `INSERT … ON CONFLICT DO NOTHING` on Postgres / `INSERT OR IGNORE` on SQLite (we'll branch by dialect in the migration).

### Why no `tenant_id` alias

The codebase has `tenant_id` references in `audit.py` (free-text). We're standardising on `organization_id`. `tenant_id` will be deprecated in TMX-3017 (rationalisation). Out of scope here; flagged for the next loop.
