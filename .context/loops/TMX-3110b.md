## 1. Task

Phase 2 of TMX-3110: ship a read-only coverage audit that, per `job_id`, compares the v1 chain (`AuditLogEntry` rows linked via `AuditRecord.job_id`) against the v2 chain (`AuditEventV2` rows for the same `job_id`). The script reports per-job pass/fail, missing-in-v2 / missing-in-v1 buckets, per-event-type counts, and a `legacy_jobs_no_v2` bucket for pre-Phase-1 jobs (legitimate historical asymmetry — surface but pass).

Why now: TMX-3110 Phase 1 (a23b0eb) wraps every v2 emit in a broad-except — failures are logged at WARNING but do NOT block v1. The within-v2 verifier (TMX-3104) detects sequence gaps but CANNOT detect "v1 has 7 events / v2 has 6" because it never reads v1. This script closes that cross-chain gap.

Addenda at play: **A1** (audit-by-default; this IS audit self-instrumentation), **A10** (program brain — operator-facing tool; markdown summary lives under `docs/audit-extracts/`).

## 2. Spec — acceptance criteria

- [ ] AC-1: for a job with N v1 events all mirrored in v2 (same set of event_types), JSON reports `{"job_id": ..., "v1_count": N, "v2_count": N, "missing_in_v2": [], "missing_in_v1": [], "pass": true}` for that job.
- [ ] AC-2: for a job where v2 is missing 1 event (simulated by deleting one v2 row), reports `missing_in_v2: [{"event_type": ..., "v1_sequence_index": ..., "timestamp": ...}]` and `pass: false`. Exit code non-zero.
- [ ] AC-3: for a job where v1 is missing 1 event (simulated symmetrically — extra row on v2 side), reports `missing_in_v1: [...]` with event_type + v2_sequence_index, `pass: false`. Exit code non-zero.
- [ ] AC-4: jobs with no v2 chain at all are listed in a `legacy_jobs_no_v2: [{"job_id": ..., "v1_count": N}, ...]` bucket — these PASS by definition (pre-Phase-1) but are surfaced so the operator can target them for TMX-3109 (historical migration).
- [ ] AC-5: exit code 0 if all jobs pass; non-zero if any job fails (missing_in_v2 or missing_in_v1 non-empty for any non-legacy job).
- [ ] AC-6: markdown summary written to `docs/audit-extracts/v1-v2-coverage-<YYYY-MM-DD>.md` with per-job table + aggregates (total jobs, jobs PASS, jobs FAIL, legacy_jobs_no_v2 count, total v1 events, total v2 events, total missing_in_v2, total missing_in_v1).
- [ ] AC-7: script accepts `--job-id <id>` for targeted runs and `--limit N` for sampling.

Out of scope:
- Phase 3 (consumer swap to read v2) — TMX-3110c
- Phase 4 (v1 emit removal) — TMX-3110d
- Historical v1→v2 migration — TMX-3109 (this script identifies *which* jobs need migrating; it does not migrate them)
- Per-event hash/integrity verification (that's TMX-3104's job; this script only counts presence/absence by event_type)
- Cross-tenant aggregation report (single-org scope; script reads whatever is in the DB)

## 3. Design

**Pattern**: read-only SQLAlchemy queries against `AuditLogEntry` + `AuditEventV2`. Bridge between v1 and v2 is the shared `job_id` string — both `AuditRecord.job_id` (v1's translation_jobs_queue.job_id) and `AuditEventV2.job_id` (regulatory translation_jobs.id) carry the same value because graph.py double-writes pass `state['job_id']` to both writers.

**Algorithm**:
1. SELECT DISTINCT job_id FROM `audit_records_queue` WHERE job_id IS NOT NULL → set V1.
2. SELECT DISTINCT job_id FROM `audit_events_v2` → set V2.
3. For each job in V1 ∪ V2:
   - load v1 events (join AuditLogEntry on audit_id where AuditRecord.job_id = job) → list of (event_type, sequence_index, timestamp).
   - load v2 events (filter AuditEventV2.job_id = job) → list of (event_type, sequence_index, event_ts_utc).
   - if v2 list is empty AND v1 list non-empty → bucket "legacy_jobs_no_v2".
   - else: compute multiset-diff by event_type → `missing_in_v2` (in v1 but not v2 for the count) + `missing_in_v1` (reverse).
   - PASS iff both missing lists are empty.
4. Aggregate; emit JSON to stdout; write markdown to `docs/audit-extracts/v1-v2-coverage-<DATE>.md`.
5. Exit non-zero if any job FAILed.

**Multiset comparison nuance**: a job legitimately has multiple `JOB_STARTED` events if it ran twice. So we don't simply do `set(v1_types) - set(v2_types)`; we compare `Counter(v1_types)` vs `Counter(v2_types)` and the difference IS the missing-set. The "missing entry" listed in the report names the event_type + the v1_sequence_index of the FIRST unmirrored occurrence (or v2_sequence_index for missing_in_v1). This is intentionally coarse — finer-grained matching (by timestamp proximity) is reserved for TMX-3109 migration tooling, not coverage detection.

**Mirror of `audit_worksheet_drift.py` style**:
- argparse with `--root`, `--limit`, `--job-id` flags.
- `_reconfigure_stdout_utf8()` for Windows console.
- Exit code 0 / 1 / 2 (2 for environmental errors like "loops dir missing"; here, "DB not initialised").
- JSON to stdout, markdown to file.

**Why standalone script and not a pytest fixture / dashboard endpoint**:
- Standalone CLI is what SREs / operators run during incident triage; a pytest fixture would only exercise during CI.
- Dashboard endpoint would couple a regulatory tool to the web layer — A1 says audit infra is the strongest asset; keeping it offline-runnable matters.
- Future scheduled cron run (TMX-3110b-cron, spawn-candidate) reuses the script verbatim.

**Alternatives considered + rejected**:
- *Put coverage check inside TMX-3104 verifier* — rejected; verifier scope is within-v2 integrity. Mixing scopes obscures both.
- *Generate report from web UI endpoint* — rejected; couples regulatory tooling to a runtime path. A1 demands offline reproducibility.
- *Skip the markdown file; JSON-only output* — rejected; AC-6 demands markdown for `docs/audit-extracts/` consistency with the existing audit reports (`loop-pytest-report-*.md` etc.).

- **Item #4 boundaries**:
  - 0-event jobs: not in either V1 or V2 set; not scanned. ✓
  - jobs with 0 v2 events but v1 events: bucketed into `legacy_jobs_no_v2` (AC-4 tested). ✓
  - jobs with thousands of events: multiset Counter is O(N); per-occurrence slicing is O(N) per event_type. For N=10k events the script runs sub-second per job; query overhead dominates. Acceptable.

(b) false-red — script reports FAIL when no real gap. Test against live DB found 9 such jobs; the report explains the root cause (v2 has event types v1 doesn't); spawn-candidate TMX-3110b-tune to add an ignore-list flag once Phase 3 consumer swap lands.

## 7. Fix

Two findings emerged during build/red-team:

1. **TenantContextMissing on first run** — the v1/v2 audit tables are tenant-scoped. The initial script implementation queried them without a tenant context and the `_filter_by_tenant` event listener raised. Fixed by adding `.execution_options(include_other_tenants=True)` to all four queries — this is the documented opt-out for "forensic/admin paths" per `app/models/tenant_scoped.py:87`. Justified explicitly in the script docstring + inline comment.

2. **Stdout noise from `app/core/database.py`** — module-level `print(f"DEBUG: Using DATABASE_URL=...")` + `print("Database tables created successfully.")` corrupt the script's JSON-to-stdout output channel. The test helper now strips lines before the first `\n{\n` so the JSON document parses cleanly. Pre-existing tech debt (CLAUDE.md conventions say "no `print()` in app/"); not in scope to fix here. Spawned candidate: TMX-3110b-quiet-db (suppress those prints to logger.debug).

Both fixes validated: 5/5 pass; script runs cleanly against the local DB.
