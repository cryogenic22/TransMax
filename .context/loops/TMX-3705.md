## 1. Task

Per addendum A3 + plan E5: today `app/api/documents.py:create_document` validates uploaded files by **filename extension only** — `evil.exe` renamed to `evil.pdf` passes through and gets stored on disk. There is no size cap (any client can DoS the disk with one 10GB upload), no magic-byte sniff, and no AV scan hook. This is a regulated translation product; uploaded files often contain PHI/PII.

This loop builds a single validation service that every upload route can use:
- magic-byte sniff (PDF, DOCX, TXT)
- size cap (configurable; default 50MB)
- AV scan trigger hook (logs structured event today; deployment wires clamd / Cloud DLP)
- fail-loud per A3: rejection raises `HTTPException 400` with a category, never silently truncates or skips

**Blast radius**: every authenticated upload route. Reduces attack surface; enforces hard storage limits. Behavioural change: previously-accepted invalid files now reject with 400.

**Addenda**: A3 (no silent fallbacks), A1 (validation events emit audit footprint via the AV trigger hook).

## 3. Design

**One pass, not two**: a naïve implementation reads the file twice — once to validate, once to save. We do it in one pass: `validate_and_save_upload` reads `read_chunk` bytes, validates magic, then continues streaming chunks to disk, tracking total bytes against the cap. On rejection (magic mismatch, oversize, decode failure), the partially-written file is deleted before raising.

**Why magic-byte sniff and not MIME-type from `UploadFile.content_type`**: the `Content-Type` header is client-supplied. A magic-byte sniff reads the actual file bytes, which is the only trustworthy signal.

**Why hardcoded magic bytes, not python-magic / libmagic**: libmagic has C dependencies and Windows is fragile. PDF/DOCX/TXT are the only formats v3.0 accepts; a 4-byte prefix check is sufficient and zero-dependency.

**Why TXT is special**: no magic bytes for plain text. We attempt UTF-8 decode; on failure try Latin-1 + heuristic NUL-byte rejection. A pathological binary file pretending to be `.txt` will likely have NUL bytes within the first 4KB, which we sample.

**Why fail-loud (HTTPException 400)**: per addendum A3, regulated paths reject explicitly. Silent truncation or fallback to "let it through anyway" creates an audit trail with corrupt data.
