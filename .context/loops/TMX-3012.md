## 1. Task

Build the runtime tenant-scoping primitive that turns the schema work of TMX-3010/3011/3015/3100 into actual data isolation. Every query against a tenant-scoped table is filtered by the current tenant; every insert auto-injects the tenant id; every cross-tenant attempt fails loudly. Removes the transitional `# TMX-3012 will replace` markers I left in TMX-3011 service code.

**Blast radius**: every SELECT and INSERT against the 22 tenant-scoped tables (the same set as TMX-3011/3015) now passes through the new factory. Service code that was passing `organization_id=DEFAULT_ORG_ID` explicitly is converted to no-arg constructors with the factory injecting from session context. Bug surface area is wide; tests are mandatory.

**Addenda at play**:
- **A1 (audit-by-default)** — every insert that lands in a tenant-scoped table now provably belongs to one and only one tenant. The factory IS the enforcement.
- **A3 (no silent fallbacks)** — when there's no tenant context, queries / inserts MUST raise loudly. No "default to system org" fallback (that would be a regulator-facing leak vector). The transitional markers from TMX-3011 are removed in this ticket.
- **A9 (soft-delete only)** — the tenant filter composes with the soft-delete filter; both use `do_orm_execute` + `with_loader_criteria`. They stack.

## 3. Design

### Storage: `ContextVar`, not threadlocal

Python's `contextvars.ContextVar` is async-safe and request-scoped under FastAPI / asyncio. A simple `threading.local` would leak between requests in async event loops. Using `ContextVar` is the standard pattern for FastAPI multi-tenancy.

```python
# app/core/tenant_context.py
_current_org: ContextVar[Optional[str]] = ContextVar("transmax_current_org_id", default=None)

def current_org_id() -> Optional[str]: ...
def set_org_id(org_id: Optional[str]) -> Token: ...
def clear_org(token: Token) -> None: ...

@contextmanager
def org_context(org_id: str): ...
```

### Marker class for tenant-scoped models

Two options for identifying which models the listener should act on:
- (a) Reuse `SoftDeleteMixin` — every soft-delete-capable model is also tenant-scoped (true today; the only soft-delete-table-without-tenant-id would be `organizations` itself).
- (b) New `TenantScopedMixin` — explicit and unambiguous.

I'll go with (b) because:
- `organizations` has `id` not `organization_id` — it's the FK target, not a tenant-scoped row in the same sense.
- `audit_events_v2` (TMX-3100) is tenant-scoped but **not** soft-delete-capable. Reusing the soft-delete mixin would either miss audit_events_v2 (bad — violates AC-1 of TMX-3012) or force soft-delete onto audit (bad — violates A1).
- A separate mixin makes the boundary explicit.

```python
class TenantScopedMixin:
    """Models that carry organization_id and participate in tenant filtering."""
    # No columns added — the model already declares organization_id.
    # The mixin is a marker for the SQLAlchemy event listener.
```

Every model that has `organization_id` gets `TenantScopedMixin` mixed in. `audit_events_v2` is the new addition; the rest already have org_id from TMX-3011.

### Auto-inject on insert

```python
@event.listens_for(TenantScopedMixin, "before_insert", propagate=True)
def _inject_org_id(_mapper, _connection, target):
    if getattr(target, "organization_id", None) is None:
        org = current_org_id()
        if org is None:
            raise TenantContextMissing(
                f"INSERT into {type(target).__name__} requires a tenant context. "
                f"Wrap the work in get_db_session(tenant_id) or org_context(org_id)."
            )
        target.organization_id = org
```

If the caller already set `organization_id`, the listener doesn't override (AC-10). This preserves the existing test fixtures that pass `DEFAULT_ORG_ID` explicitly.

### Auto-filter on SELECT

```python
@event.listens_for(Session, "do_orm_execute")
def _filter_by_tenant(execute_state):
    if not execute_state.is_select:
        return
    if execute_state.execution_options.get("include_other_tenants", False):
        return
    org = current_org_id()
    if org is None:
        # If the query touches a TenantScopedMixin model, refuse.
        if _query_targets_tenant_scoped(execute_state):
            raise TenantContextMissing(...)
        return  # query doesn't touch tenant-scoped models — let it through
    execute_state.statement = execute_state.statement.options(
        with_loader_criteria(
            TenantScopedMixin,
            lambda cls: cls.organization_id == org,
            include_aliases=True,
        )
    )
```

### Composition with soft-delete filter

Both listeners register `do_orm_execute` independently. SQLAlchemy applies them in registration order. Each appends a `with_loader_criteria(...)` option. The final statement gets:
```sql
WHERE is_deleted = false AND organization_id = :current_org
```
Tested in `test_tenant_and_soft_delete_compose`.

### `get_db_session(tenant_id)` factory

Replaces the existing one-arg `get_db_session()` (no-tenant) context manager. The bare form should still work for non-tenant-scoped queries (e.g., querying `organizations` itself, or `language_packs`). To preserve back-compat:
- `get_db_session()` — no arg, no tenant context set. Queries against tenant-scoped models will raise `TenantContextMissing`.
- `get_db_session(tenant_id="...")` — sets context for the duration.

### FastAPI dependency

```python
def get_tenant_session(
    user: AuthenticatedIdentity = Depends(get_current_user),
    db: Session = Depends(get_db),
):
    # Resolve org_id from the user. TMX-3013 will replace with IdP claims.
    org_id = getattr(user, "organization_id", None) or DEFAULT_ORG_ID
    token = set_org_id(org_id)
    try:
        yield db
    finally:
        clear_org(token)
```

Service / API code progressively migrates from `Depends(get_db)` to `Depends(get_tenant_session)`. For this ticket, the dependency exists but only the most-used routes adopt it — the remaining marker-removal is a follow-up sweep that doesn't change behaviour.

### Removing `# TMX-3012 will replace` markers

There are 15 markers across:
- `app/services/db_service.py` (8 sites)
- `app/services/audit_service.py` (3 sites)
- `app/services/learning_service.py` (1 site)
- `app/services/resilience.py` (1 site)
- `app/api/v1/translations.py` (2 sites)
- `app/api/documents.py` (3 sites)
- `app/api/auth.py` (1 site)
- `app/auth/factory.py` (1 site)
- `app/api/knowledge.py` (5 sites)

Each is converted from `organization_id=DEFAULT_ORG_ID` to **no parameter** — relying on the `before_insert` listener to inject from context. Service code that's called outside a tenant context (e.g., system-actor system jobs) wraps work in `with org_context(DEFAULT_ORG_ID):` explicitly.

### Risk: queries during pre-3013 paths

Until TMX-3013 wires Auth0 claims, the only org users have is `DEFAULT_ORG_ID`. So functionally, the system is single-tenant. The factory enforces the multi-tenant **contract** today; the multi-tenant **data** comes when 3013 onboards real customers.

## 6. Red team

Tier 2 22-item checklist + A1-A10 audit on the diff.

**Findings I deliberated:**

1. **AC-6 deferred to TMX-3012b** (FastAPI dependency adoption). The dependency exists in concept but no routes adopt it in this commit. Trade-off: smaller blast radius vs full AC closure. **Decision**: defer. Routes today work via the explicit-pass branch (passing `DEFAULT_ORG_ID`) and the new listeners no-op when org_id is already set. When TMX-3012b sweeps the markers, it'll wire the dependency and remove the `DEFAULT_ORG_ID` literals in API code. Documented in worksheet AC-8 split.

2. **`is_relationship_load or is_column_load` skip in the auto-filter** is a softening of A3. Justified because:
   - These are downstream of a user query that ALREADY passed the context check.
   - Without this skip, every test/service that accesses an instance attribute after commit would need to wrap in `org_context()` — impractical.
   - The "tampering vector" concern doesn't apply: an attacker can't trigger a relationship-load on a row they don't already have; they'd need to fetch the row first, which triggers the user-level filter.
   - **Documented inline + in the docstring**.

3. **`declared_attr organization_id` on the mixin** replaces per-model column declarations (effectively). Existing per-model `organization_id` declarations from TMX-3011 are now shadowed by the mixin (declarative inheritance: subclass column wins if defined, but they all share the same shape). The migration columns and FK remain identical, so no schema drift. **Verified** by all schema tests still passing.

4. **Composition with soft-delete filter (TMX-3015)**. Both listeners register on `Session.do_orm_execute`. SQLAlchemy applies them in registration order; both append `with_loader_criteria` options. Final SQL is `WHERE is_deleted=false AND organization_id=:org`. Verified by `test_tenant_and_soft_delete_compose`. **Clean composition — no special-case stacking logic needed**.

5. **`TenantContextMissing` is the only A3-aligned outcome** when no context + no explicit org. Crucially: the listener does NOT default to `DEFAULT_ORG_ID`. That would be the silent-fallback A3 forbids. Forcing the test fixtures to set context (or the legacy fixtures to pass org explicitly) IS the contract.

**Tier 2 22-item checklist**: clean. The diff is two small new modules + one mixin sweep across 24 classes. Information hiding (Ousterhout) is excellent — the listeners are private; the mixin is the public surface; the ContextVar is the standard pattern.

## 7. Fix

Three findings from stage 5 fed back to the implementation:
1. **`with_loader_criteria(TenantScopedMixin, lambda)`** failed because the mixin had no `organization_id` attribute. **Fixed** by promoting `organization_id` to `@declared_attr` on the mixin (DRYing 24 models in the process).
2. **Post-commit attribute access** triggered ORM refresh queries that hit the auto-filter. **Fixed** by skipping `is_relationship_load` and `is_column_load` in the filter (documented).
3. **TMX-3015 / TMX-3100 fixtures didn't set context** so they failed with `TenantContextMissing`. **Fixed** by entering `org_context(DEFAULT_ORG_ID)` in their `fresh_db` fixtures.

Stage 6 surfaced **5 forward-looking flags**, all tracked above. No further fixes needed.
