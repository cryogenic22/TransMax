## 1. Task

Expose `app/services/audit_verifier_v2.py:AuditVerifierV2.verify_job_chain(job_id)` via a `GET /api/v1/audit/{job_id}/verify_v2` endpoint. Returns a JSON `VerificationReport` (event_count, ok_count, findings list with finding-class + sequence_index + detail) so a pharma reviewer can independently verify the v2 audit chain integrity without leaving the UI.

**Addenda at play**:
- **A1** (audit-by-default) — verifying the chain is a regulator-facing action. Per TMX-3104a (spawned), we should emit a `VERIFICATION_REQUESTED` audit event. **Judgment call**: TMX-3104a is already a spawned follow-up explicitly deferred from TMX-3104. We keep that deferral here — emitting an audit event for every verify hit would (a) pollute the chain with read-only reviewer noise and (b) introduce a circular write-then-verify dependency. Documented as A1-deferred-to-TMX-3104a; not a silent fallback because the spawned ticket exists and is tracked.
- **A3** (no silent fallbacks) — load-bearing. A corrupted chain MUST return `is_valid: false` with the findings list, NEVER `is_valid: true` or a generic 200/empty. Verifier errors (tenancy missing, job nonexistent) MUST be loud.
- **A4** (dual-model layer) — touches only v2 models via the existing verifier. v1 audit endpoint (`/api/v1/audit/{audit_id}`) is untouched.
- **A5** (stable IDs) — endpoint keys on `job_id` (the regulatory translation_jobs FK, same as TMX-3100's audit_events_v2.job_id).
- **A6** (LLMs are qualified suppliers) — not triggered (no LLM call in this loop).

**Naming choice (path)**: existing `/api/v1/audit/{audit_id}/verify` is the v1 path keyed by `audit_id` (legacy `AuditRecord.audit_id`). To avoid path collision and to make the v2 nature explicit at the URL (a regulator clicking the URL must know which ledger they're checking), the new route is `GET /api/v1/audit/{job_id}/verify_v2`. Ticket text says `/verify`; the loop chooses `/verify_v2` to (a) not break the existing v1 verify route + its test, (b) make the ledger version visible at the URL, (c) leave a clean swap path when TMX-3109 migrates v1 callers and we can promote v2 to canonical `/verify`. Documented as a deliberate spec-to-design clarification.

## 2. Spec — acceptance criteria

- [x] AC-1: `GET /api/v1/audit/{job_id}/verify_v2` returns 200 + `{"ok": true, "organization_id": "<org>", "job_id": "<job>", "event_count": N, "ok_count": N, "findings": []}` for a valid chain with N events.
- [x] AC-2: returns 404 with `{"detail": "No v2 audit chain found for job <id>"}` if the job has zero events in `audit_events_v2`. (A3 — loud "no chain" signal, not a 200 with empty findings that the reviewer could misread as "all clear".)
- [x] AC-3: returns 200 + `{"ok": false, "event_count": N, "ok_count": N-1, "findings": [{"sequence_index": K, "finding": "tampered_payload", "event_id": "<id>", "detail": "..."}]}` when a payload row is mutated post-write. (A3 — never claim ok:true on a corrupted chain.)
- [x] AC-4: returns 200 + findings list containing `tampered_event_hash` on event K and `broken_chain` on event K+1 when event_hash is mutated mid-chain (the canonical TMX-3104 cascade).
- [x] AC-5: enforces tenant scoping — a job belonging to org A is invisible to a verifier called under org B's context, returning 404 (NOT 403) to avoid leaking existence of cross-org job ids.
- [x] AC-6: response is small (`< 100 KB` for chains with up to ~500 events — `findings` only contains DEFECT events, not OK events; OK chains return zero findings).
- [x] AC-7: response model is a Pydantic schema (`AuditVerificationResponse`) auto-documented in OpenAPI — reviewer can hit `/api/v1/docs` and see the contract.

**Out of scope**:
- Auth/AC-401: the broader API has `AUTH_MODE="none"` in dev pilots; auth gating is owned by TMX-3013 (Auth0 wiring). When TMX-3013 lands, this endpoint inherits the global auth dependency. We do NOT add a one-off `Depends(current_user)` here that diverges from the rest of `/api/v1/audit`.
- Merkle anchor verification (TMX-3104b spawned from TMX-3104).
- `VERIFICATION_REQUESTED` audit event emission (TMX-3104a spawned from TMX-3104).
- Scheduled background verifier (TMX-3104c spawned from TMX-3104).
- Bulk org-level verify endpoint (could be `GET /api/v1/audit/verify_org_v2`; not in this ticket — single-job is the reviewer's primary path).

## 3. Design

**Approach**: Add one route to `app/api/v1/audit.py`. The route:
1. Reads the current org from `TenantContextMiddleware` (already wired in `app/main.py`).
2. Constructs `AuditVerifierV2(session_factory=SessionLocal)`.
3. Pre-checks the chain exists by counting rows for `(org_id, job_id)` in `audit_events_v2`. If zero, return 404 (A3 + AC-5 — for jobs in OTHER orgs the auto-filter ensures the count is also 0, so cross-org access also lands on 404, not 403).
4. Calls `verifier.verify_job_chain(job_id)`.
5. Maps `VerificationReport` → `AuditVerificationResponse` Pydantic model with `ok` (alias for `is_valid`), `event_count`, `ok_count`, `findings: list[VerifyFindingResponse]`.

**Why count-first instead of relying on report.event_count == 0**: The verifier already correctly returns `VerificationReport(event_count=0, ok_count=0, findings=[])` for empty chains (and notes "empty-chain jobs are valid by construction"). Returning 200 + `ok:true` on a job with no events is a silent-fallback hazard for a reviewer who fat-fingers a job_id — they'd see "all clear" for a job that doesn't exist. The pre-check upgrades this to a loud 404. (A3.)

**Schema model**: One new Pydantic model `AuditVerificationResponse` + one `VerifyFinding`. Fields mirror `VerificationReport`/`EventReport` directly so JSON ↔ dataclass mapping is a per-field copy with no logic. `finding` is the string value of `EventFinding` enum (the enum already inherits `str`).

**Alternatives considered**:
- Use `verify_org_chain()` and filter to one job — rejected. `verify_job_chain` is the purpose-built API; using the org method would do extra DB work.
- Skip the count-pre-check, accept the verifier's empty-chain-is-valid behaviour — rejected per A3 above.
- Mount the new route on a separate `audit_v2_router` — rejected. The existing `audit` router is already namespaced under `/api/v1/audit`, and a single per-job verify endpoint doesn't justify a new router. When TMX-3109 swaps v1→v2 callers, the path will be promoted to `/verify` (no `_v2` suffix) inside the same router; no router churn needed.
- Add auth dependency `Depends(get_current_user)` — rejected for this ticket. The rest of `/api/v1/audit` has no auth dependency today; AUTH gating is TMX-3013's job. Adding a one-off here would create policy drift (some routes 401, others 200). The TenantContextMiddleware already enforces org scoping which is the higher-value guarantee.

**Five-test G1 anti-bloat rubric**:
- (a) Code path needed? YES — no existing endpoint exposes the v2 verifier; without this, the only consumer is a Python test.
- (b) <5 callers? YES (1 new route, 1 new response model).
- (c) Bundle impact? Negligible (~80 LOC).
- (d) Reuses existing patterns? YES — same `Depends(get_db)` / `APIRouter` / Pydantic-response pattern as the rest of `audit.py`.
- (e) Ships with a failing-before-the-change test? YES — `tests/test_audit_verify_endpoint.py` calls the route before it exists → 404. After the route lands → all green.

## 6. Red team

22-item Tier 2 checklist applied to the diff:
- **Deep modules**: route is thin (~30 LOC). Verifier service stays the deep module. OK.
- **Information hiding**: route doesn't expose internal `EventFinding` enum values to anyone but the JSON consumer — finding strings ARE the API contract intentionally (reviewer needs them).
- **Different layer different abstraction**: route ↔ Pydantic ↔ verifier dataclass ↔ ORM. Each layer has its own type, no leakage.
- **Define errors out of existence**: not strictly applicable — the verifier intentionally REPORTS errors (findings) rather than raising. Route preserves this.
- **A1 audit-by-default**: deferred to TMX-3104a (explicitly tracked, not silent).
- **A3 no silent fallbacks**: every failure path is explicit (404 for missing chain, 200 + `ok:false` + populated findings for corruption, propagated TenantContextMissing for misconfigured deployment).
- **A4 dual-model**: v2-only; v1 audit route untouched.
- **A5 stable IDs**: path keyed by `job_id`, finding rows carry `event_id`.
- **A9 soft-delete**: read-only endpoint, no deletes.
- **Bloat**: 5/5 anti-bloat rubric (stage 3).
- **Test discipline**: tests prove behaviour change (4-class corruption matrix + tenant isolation + 404 + small-response), not coverage padding.
- **Backwards compatibility**: pure addition. Existing `/api/v1/audit/{audit_id}` and `/api/v1/audit/{audit_id}/verify` routes unchanged.
- **No `Any`**: response model is typed.
- **No bare except**: none added.
- **No `print()`**: none added.
- **Naming**: `/verify_v2` is unambiguous (vs collision with v1 `/verify`).
- **Logging**: route doesn't log; verifier already logs internally where needed.
- **Error message detail leakage**: 404 returns `"No v2 audit chain found for job <id>"` — leaks job_id back to caller. Acceptable because caller supplied it and the auto-tenant-filter ensures no cross-org existence leak.
- **Path-traversal / injection**: `job_id` is bound via FastAPI path param (string) and used in SQLAlchemy parameterised queries inside the verifier. Safe.
- **Rate limiting**: not applied; verifier is read-only + bounded (one chain walk). Out of scope. Could be follow-up if abused.

**Edge cases checked in tests**:
- Empty chain → 404 (AC-2)
- 1-event chain valid → 200 ok:true (AC-1)
- Tampered payload → 200 ok:false + tampered_payload finding (AC-3)
- Tampered event_hash mid-chain → 200 ok:false + tampered_event_hash + broken_chain cascade (AC-4)
- Cross-tenant access → 404 (AC-5)
- Response size sanity → response JSON < 100 KB (AC-6)
- OpenAPI contract present → response_model declared, visible in /openapi.json (AC-7)

**Potential surprises**:
- TestClient runs through full middleware stack including `TenantContextMiddleware`, which sets context to `DEFAULT_ORG_ID` for every request. AC-5 (cross-tenant) cannot be tested via plain TestClient hits to the route because all hits get the SAME org context. Solution: AC-5 test writes the audit event under a DIFFERENT org (using `org_context(org_b)`), then hits the route — the middleware sets context to `DEFAULT_ORG_ID` which CANNOT see org_b's events. That's the right behavioural test: the route, under whatever-the-middleware-resolves-to org, cannot see events written under a different org.
