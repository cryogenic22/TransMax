## 3. Design

**Pattern**: After each v1 emit, do a v2 emit inside a broad-except block. Pseudocode:

```python
audit_svc.log_event(audit_id, "JOB_STARTED", payload)  # v1: unchanged
try:
    # Phase 1 double-write: v2 failures are logged but don't block v1 — see TMX-3110 worksheet stage 3
    _v2_writer().record_event(
        job_id=state['job_id'],
        event_type="JOB_STARTED",
        actor_id=None,
        actor_kind="system",
        payload=payload,
    )
except Exception as exc:  # noqa: BLE001 — see comment above; broad-except is intentional, removed in Phase 4 / TMX-3110d
    logger.warning(
        "v2 audit emit failed (event_type=%s, job_id=%s, reason=%s) — "
        "v1 chain unaffected, v2 chain has gap (TMX-3104 verifier will report)",
        "JOB_STARTED", state['job_id'], exc,
    )
```

**Why broad-except is justified despite A3** (no silent fallbacks):

1. Phase 1's contract is "v2 chain catches up WITHOUT changing v1's contract". A v2 failure that propagated would break v1's caller — that's a functional regression dressed as compliance theatre.
2. Failure IS surfaced — at WARNING level with structured context (event_type, job_id, reason) — not silently swallowed. TMX-3104's verifier will independently flag any missing-event sequence gap during the next verification cycle, so the gap is detected by the canonical defence-of-evidence mechanism.
3. The wrapper has an explicit lifespan: Phase 4 (TMX-3110d) inverts the responsibility — v2 becomes mandatory, v1 becomes optional, broad-except moves to v1.

**Actor resolution per site**:

| Site | actor_id | actor_kind | Rationale |
|---|---|---|---|
| S1-S3 (validate_request — `AUDIT_TRAIL_INITIALIZED`, `CONFIG_SNAPSHOT_CAPTURED`, `JOB_STARTED`) | `None` | `"system"` | Job-start is system-initiated; no human action; no specific agent — this is the pipeline boot |
| S4 (quality_gate — `SCORECARD_GENERATED`) | `"quality_gate"` | `"agent"` | The quality-gate node IS the agent emitting this; node-name is the stable identifier |
| S5 (finalize_job — `JOB_FINALIZED`) | `"finalizer"` | `"agent"` | The finalize node decides the final job status; agent-emit |

A6 (qualified-supplier) propagation: v1's JOB_STARTED payload contains `doc_id` + `timestamp`. v2's payload contains the same. The hardcoded `"model": "gpt-4o"` in the CONFIG_SNAPSHOT path (graph.py:144) is a known bug (TMX-3202); we preserve the exact payload v1 captures, so the bug propagates identically. Fixing it would mix scopes — explicitly out of scope.

**Where the writer is constructed**: a lazy module-level `_audit_writer_v2 = None` with a `_get_audit_writer_v2()` factory, matching the existing `get_audit_service()` / `get_db_service()` pattern. The writer takes `app.core.database.SessionLocal` as its session factory.

**Why not push the v1+v2 pairing into AuditService itself?** That would couple v1 to v2 inside `audit_service.py` — a structural change that complicates Phase 4 removal. Doing it at the call site keeps the v1 module untouched (one-way clean revert path), the v2 emit visible at every site (auditable diff), and Phase 4's removal of v2 emits site-by-site rather than a single library deletion.

**Alternatives considered + rejected**:
- *AuditService.log_event auto-mirrors to v2 internally* — rejected; couples v1 to v2; harder to revert; obscures the call-site contract.
- *Aspect/decorator around AuditService methods* — rejected; magic; doesn't survive Phase 4's removal cleanly.
- *Swap all 5 sites at once and remove v1 in this loop* — rejected; violates Phase 1 contract; user explicitly said don't.
- *Defer S4/S5 to Phase 1b* — considered; rejected because S4/S5 share the same actor-resolution rules and test fixtures as S1-S3, so co-shipping is cheaper than two loops.

- **Failure mode if wrong in production**: v2 chain has gaps; verifier reports; v1 chain still valid; bundle export reads v1 — no GxP regression. Worst case: false sense that v2 chain is complete. Mitigated by AC-5 test + WARNING log + verifier sequence-gap finding.

## 7. Fix

Two findings emerged during red team:

1. **`actor_id` GUID schema constraint** — caught during test 5 RED→GREEN. Loop spec said actor_id=<node_name> but schema types it as GUID. Pivoted: actor_id=None, node-name in `payload['_actor_node']`. Spawned TMX-3110-actor-id-schema. Documented in stage 4 table.
2. **Test-infrastructure cascade** — `app.services.db_service.SessionLocal` is bound at module-import time; the `fresh_engine_for_db` fixture only swaps `app.core.database.SessionLocal`. Fixed via the `fresh_db_with_org` fixture which `monkeypatch.setattr`s the downstream bindings (mdb.SessionLocal, dbs.SessionLocal, dbs.engine) and resets the DatabaseService singleton. Without this fix, 4 of 7 tests passed in isolation but failed mid-suite-run when ordering changed. This is a pre-existing brittleness in the test harness; the fixture-level fix is localised to this file so it doesn't disturb other tests.

Both fixes validated: 7/7 pass alone, 875/875 pass in full suite (882 total — including 2 skipped). Net delta: +7 tests, 0 regression.
