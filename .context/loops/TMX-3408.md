## 1. Task

Eval suite `tests/evals/data/en_es/critical_safety.jsonl` case `number_001`:

```json
{"id": "number_001", "kind": "tampered",
 "source": "Take 10 mg twice daily.",
 "target": "Tome 100 mg dos veces al dia.",
 "expected_defects": [{"category": "NUMERIC_MISMATCH", "severity": "CRITICAL"}],
 "rationale": "Dose 10 mg -> 100 mg. NUMERIC_MISMATCH must fire."}
```

Today's behaviour: NUMERIC_MISMATCH does NOT fire. The eval reports
`"tampered missed expected CRITICAL defects: ['NUMERIC_MISMATCH'] (got ['FREQUENCY_MISMATCH', 'UNIT_MISMATCH'])"`.

A patient receiving 100 mg instead of 10 mg is the canonical worst-case for this product — order-of-magnitude dosage tampering must hard-block. This is the exact failure mode A2 (quality at gates, not in translate) is supposed to catch deterministically.

**Root cause** (`app/services/language_packs/spanish.py:33-47` `SpanishPack.check_numbers`):

```python
def check_numbers(self, source: str, target: str) -> List[Dict[str, Any]]:
     vocab = re.findall(r'\b\d+(?:[\.,]\d+)?\b', source)
     violations = []
     for num in vocab:
         if num not in target:                              # <-- substring check!
             alt = num.replace('.', ',')
             if alt not in target:
                 violations.append(...)
     return violations
```

For source num `"10"` and target `"Tome 100 mg dos veces al dia."`, `"10" in "100"` is `True` because Python's `in` is substring containment, not word-boundary matching. The number "10" is "found" inside "100" and no defect fires.

**Blast radius**: every Spanish-target eval case where a source number is a digit-prefix of a target number was passing silently. The fallback generic numeric check at `app/services/quality_gate.py:120-140` already uses `\b...\b` word boundaries — Spanish pack regressed against the fallback when the pack overrode it.

**Addenda at play**: A2 (quality at gates), A3 (no silent fallbacks — this *was* a silent fallback, masquerading as a passing check).

**Sister bug**: `good_001` (TMX-3409) — `check_frequency` lacks Spanish patterns, producing a spurious FREQUENCY_MISMATCH on the same case (and on canonical Spanish translations). Fixed in next loop.

## 3. Design

The fix is a regex change in one method. No design tradeoff worth an ADR.

**Algorithm**:
1. Extract source numbers via `\b\d+(?:[\.,]\d+)?\b` (unchanged).
2. For each source number, build a candidate set of acceptable forms: `{num}` always, plus the comma↔dot swap (Spanish-canonical decimal comma).
3. For each form, search target for `\b{escaped_form}\b` (re.search). If any form matches, the number is preserved.
4. Otherwise: emit NUMBER_MISMATCH.

**Why `\b...\b` and not `(?<!\d)...(?!\d)`**: `\b` already encodes the digit-vs-non-digit boundary correctly for our token set (numbers are digit runs ending at a non-digit, which `\b` captures). Adding lookarounds is over-engineering for this pattern.

**Why both directions of comma-swap**: Source EN typically uses `.` for decimals; Spanish target typically uses `,`. But machine-translation systems sometimes leave `.` as-is. Accept both.
