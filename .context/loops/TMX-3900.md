## 1. Task

Per plan E9 + addendum A6: every node in the LangGraph translation pipeline must emit a structured span so we can answer "where did this job spend its 12 seconds?" without parsing free-form logs. Today there's an in-memory `ObservabilityService` (custom counters); production needs OpenTelemetry-shaped spans that export to a collector (Jaeger / Tempo / Datadog / Honeycomb — chosen at deploy time via env vars, not code).

This loop adds the OTel scaffolding so every graph node emits a span. LLM-call child spans, span attribute capture for `prompt_version`/`content_hash`, OTLP collector config, and integration with the existing `ObservabilityService` cost tracking are deliberately deferred to follow-ups.

**Blast radius**: 7 graph nodes wrapped with a span. Span emission is opt-in via env var (`TRANSMAX_OTEL_ENABLED`); when disabled, the tracer is a no-op so production cost is zero. Tests run with the no-op tracer by default.

**Addenda**: A6 (qualified-supplier observability), A1 (audit chain has timestamps; OTel has spans — they complement, not replace).

## 3. Design

**Why decorator, not LangGraph middleware**: LangGraph node functions are plain `async def state -> state`. A decorator is the cheapest way to add span coverage without restructuring the graph wiring. If LangGraph adds a middleware API later, we migrate.

**Why opt-in via env var**: span emission has a small but non-zero cost. Tests + dev runs don't need it. Production turns it on with `TRANSMAX_OTEL_ENABLED=1` plus the OTLP env vars. Keeps tests fast and deterministic.

**Why ConsoleSpanExporter as default**: visible feedback during dev (spans printed to stderr); requires zero config; production overrides with OTLP at deploy time.

**Why `job_id` as the only required attribute**: that's the audit-chain join key. Other attributes (segment counts, language pair, etc.) are useful but optional — adding them is a separate code-change per node and exceeds AC-3's surgical scope. Sister loop can flesh these out.
