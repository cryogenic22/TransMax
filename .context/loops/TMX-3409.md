## 1. Task

Eval suite `tests/evals/data/en_es/critical_safety.jsonl` case `good_001`:

```json
{"id": "good_001", "kind": "canonical",
 "source": "Take one tablet by mouth twice daily with food.",
 "target": "Tome un comprimido por via oral dos veces al dia con alimentos.",
 "expected_defects": [],
 "rationale": "Canonical translation; no critical defects expected."}
```

Today's behaviour: eval reports `"canonical produced unexpected CRITICAL defects: ['FREQUENCY_MISMATCH']"`. A perfectly accurate translation gets blocked.

This is a worse failure mode than `number_001` in one sense: a false-positive on a CANONICAL translation will cause every legitimate Spanish reviewer-facing artefact to be held / re-reviewed. Pilots will see this as flakiness and lose trust in the gates.

**Root cause** (`app/services/quality_gate.py:587-592` `check_frequency`):

```python
FREQ_PATTERNS = {
    'une fois par jour': 1.0, 'once daily': 1.0,
    'deux fois par jour': 2.0, 'twice daily': 2.0,
    'trois fois par jour': 3.0, 'three times daily': 3.0,
    'quatre fois par jour': 4.0, 'four times daily': 4.0,
}
```

Patterns cover English + French only. Spanish frequencies ("una vez al día", "dos veces al día", etc.) aren't recognised. Result: source matches `twice daily` (freq 2.0); target matches nothing → `if src_freqs and not tgt_freqs:` fires, emitting a spurious FREQUENCY_MISMATCH.

**Sister effect on `number_001`**: the same root cause was contributing a spurious FREQUENCY_MISMATCH on `number_001` too (visible in pre-fix eval output: `got ['FREQUENCY_MISMATCH', 'UNIT_MISMATCH']`). The eval pass-rate for `number_001` doesn't depend on this fix because the runner only checks expected categories are present (not that no extras exist for tampered cases) — but the spurious defect would create reviewer noise in production.

**Addenda at play**: A2 (deterministic gates must not produce false-positive blocks); A3 (a canonical translation incorrectly blocked is a failure mode mirroring "mock substituted as real"); pre-pilot trust.

## 3. Design

The fix is a 4-line addition to a dict (Spanish patterns) plus an accent-fold helper. No design tradeoff worth an ADR.

**Why accent-fold instead of just adding both forms**:
- Adding both forms (`'dos veces al dia'` and `'dos veces al día'`) doubles the dict and forgets compounds (`tres veces al día`, vs `tres veces al dia`). 8 entries.
- Folding accents at lookup time: fold target text through `unicodedata.normalize('NFKD')` + drop combining marks, look up against unaccented patterns. 4 dict entries, robust to other Spanish accent edge cases (`ñ` not affected, just á/é/í/ó/ú).

I'll go with accent-fold but apply it ONLY for languages where it's safe (Spanish). The function already operates on `text.lower()`; folding before pattern check is one extra `unicodedata` call.

**Why not a separate `check_frequency_spanish` method**: the function is already cross-lingual (English + French co-exist in the same dict). Treating Spanish the same way preserves the architecture. When TMX-3411 sweeps the rest, the same pattern extends.
