**Pre-mortem**: if this fails in production, the failure mode is — (a) the allowlist is too tight, stripping legitimate Tiptap markup (bold/italic/list/link) that reviewers were relying on, silently corrupting authored translations as they save; OR (b) the allowlist is too loose, leaving a residual XSS vector (e.g. `data:` URIs, SVG `<use href>`, MathML) that a malicious DOCX-paste could exploit and which then persists on every reviewer's load. Mitigation: explicit allowlist (no defaults), positive test for legitimate markup survival, negative tests for several attack vectors, A1-style audit-event hook spawned as TMX-3050a so a regulator can see content was modified.
**Blast radius**: `frontend/components/ui/RichTextEditor.tsx` (sole consumer of `getHTML()` today), `frontend/lib/sanitizeHtml.ts` (new helper; centralised so other rich-text surfaces — DOCX-paste, comment threads — can reuse it later), `frontend/package.json` (one new prod dep: `dompurify@^3.4.2`). No backend, no DB, no API. Affects only the reviewer surface (currently the most regulated UI). No public route uses RichTextEditor yet, but it is wired to be used by TMX-3702 reviewer-frontend UX (in progress) — so this lands BEFORE the surface goes live.

## 1. Task

The 2026-05-09 audit (`TRANSMAX_AUDIT_2026-05-09.md` finding F-H03 — Critical/High open) identified a stored-XSS vector in `frontend/components/ui/RichTextEditor.tsx:83`: the `editor.getHTML()` output flows directly to `onChange` (and from there to persistence and re-render on every other reviewer's page load) without sanitisation. Tiptap's HTML parser is liberal — pasted clipboard markup with `<img onerror=…>`, `javascript:` URLs, `<script>` tags, `<iframe>`, etc. survives.

This is the *worst-case* class of XSS for TransMax: the reviewer surface is exactly where a regulator looks for "did this system protect the integrity of the regulated artefact?". A persisted XSS that fires on every reviewer's load fails that test.

**Addenda at play**:
- **A1 (audit-by-default)** — sanitisation strips content. That is a state mutation. A1 demands an audit event before the side-effect. Spawn TMX-3050a once TMX-3101 (audit ledger v2 SDK) is callable from the frontend; for now, document the design hook in stage 6.
- **A3 (no silent fallbacks)** — if DOMPurify import fails (CDN'd version somehow unavailable, dynamic-import edge), the sanitiser MUST refuse to set HTML, not pass through unsanitised. Tested.
- **A7 (one canonical IA)** — RichTextEditor lives in `components/ui/`, used (eventually) by `/workspace/review/*`. No other surface adds this dep.

## 3. Design

**Approach**: introduce `frontend/lib/sanitizeHtml.ts` exporting a single pure function `sanitizeRichTextHtml(html: string): string`. Implementation wraps `DOMPurify.sanitize(html, config)` with an EXPLICIT allowlist (`ALLOWED_TAGS` + `ALLOWED_ATTR`) — never the default profile, which is too loose for our threat model.

Allowlist (documented in code):
- Tags: `p, br, hr, h1, h2, h3, h4, h5, h6, strong, em, u, s, code, blockquote, ul, ol, li, a, table, thead, tbody, tr, th, td`.
- Attributes: `href` (on `<a>` only, scheme-restricted), `colspan`, `rowspan`, `class` (Tiptap emits class on lists/tables for styling).
- URI scheme guard: DOMPurify's `ALLOWED_URI_REGEXP` clamped to `^(?:https?|mailto):` only — strips `javascript:`, `data:`, `vbscript:`.
- Hooks: `ADD_ATTR: ['target', 'rel']` is NOT set; if a future ticket needs `target=_blank`, it must add `rel="noopener noreferrer"` in the same change.

Wire it into `RichTextEditor`'s `onUpdate`:

```ts
onUpdate: ({ editor }) => {
    onChange(sanitizeRichTextHtml(editor.getHTML()))
}
```

**Alternatives considered**:
- *Hand-rolled regex sanitiser* — rejected; this is the textbook XSS anti-pattern. Even browser-native `DOMParser`-based stripping is hard to get right against mutation XSS.
- *sanitize-html npm package* — rejected; heavier (~80KB), Node-oriented, less battle-tested in browsers than DOMPurify.
- *Trusted Types API (CSP-level)* — out of scope for v3.0; will revisit when CSP gets stricter (TMX-3615 already wired the headers).
- *Sanitise on backend ingest only* — rejected; the editor's own re-render path goes through `setContent(html)`, which means an attacker who PASTES malicious HTML into the editor would see it execute LOCALLY before the backend ever sees it. Egress-side (write) sanitisation is the right defence.

ADR not needed — this is a textbook XSS-defence pattern with no novel TransMax-specific tradeoffs.

Then implemented the helper at `frontend/lib/sanitizeHtml.ts` and discovered, over three test-driven iterations, that:

1. `USE_PROFILES: { html: true }` re-expanded the allowlist back to the full HTML profile (DOMPurify combines profiles with explicit ALLOWED_TAGS as a UNION). Removed; ALLOWED_TAGS is now the only source.
2. happy-dom (our test DOM) eagerly fetches `<iframe src=...>` resources during DOM parsing in a way that fires an unhandled async rejection AFTER DOMPurify strips the iframe. Sidestepped by using `<iframe></iframe>` (no src) in the iframe-strip test — the security property (tag is gone) is what we care about.
3. happy-dom parses `<object>...</object><embed>` as `<object>...<embed></object>` (per HTML5 fallback-content rules). When DOMPurify removes `<object>` with `KEEP_CONTENT: true`, the nested `<embed>` is promoted to body but isn't re-iterated. Mitigated with **two-pass sanitisation**: a second `DOMPurify.sanitize()` call cleans up anything promoted by the first pass. Added explicit `FORBID_TAGS` for belt-and-braces.

## 7. Fix

Red-team surfaced one tightening: the original allowlist-only design relied on DOMPurify's normal traversal to remove `<object>` and `<embed>`. happy-dom's HTML5 fallback-content parsing nests `<embed>` inside `<object>`, and DOMPurify's KEEP_CONTENT promotion-after-removal isn't re-iterated. Without action, `<object data=evil><embed src=evil>` would have a residual `<embed>` after sanitisation.

Mitigation already in the diff (see stage 5): explicit `FORBID_TAGS` denylist + **two-pass sanitisation**. The second pass cleans up anything promoted from a removed parent. Cost is microseconds; safety is "robust against parser quirks for nested mutation XSS".

No other red-team findings.
