## 1. Task

`frontend/` is a Next.js 16 codebase that currently lives as a **nested git repository** inside the parent transmax repo. The nested repo:

- Has 4 commits in its own history (`55f5270` initial → `d4f340c` rationalise nav)
- Has **no remote** (`git -C frontend remote -v` returns empty)
- Is referenced by the parent only as a dangling gitlink — `frontend/` shows as "modified content, untracked content" in `git status`
- Is not a real submodule (no `.gitmodules`, no commit hash recorded in parent)

**Net effect**: ~3,200 lines of substantive frontend work (full `/workspace/*` IA, design system, Radix UI + Tiptap + framer-motion + lucide deps) sit uncommitted on disk and **cannot be deployed**:
- No `git push` target inside the nested repo
- No CI build for the parent because the gitlink has no resolvable commit
- Railway can't pin to a frontend hash

This loop merges `frontend/` into the parent repo (option (b) of the three I drafted at TMX-3600). After this, the entire repo ships as one unit, one commit per change, one CI pipeline, one PR per logical change.

**Blast radius**: parent-repo working tree only. No backend code. No live deployments are affected — the frontend was never deployable in its current form, so de-tangling can only improve things.

## 3. Design

**Three options considered** (see TMX-3600 closing notes):

| Option | Pro | Con | Verdict |
|---|---|---|---|
| (a) Promote to formal submodule + own GitHub remote | Clean ownership split | Third repo to babysit; PRs that span FE+BE need two PRs and a sync dance; pre-pilot scale doesn't justify it | Reject for now |
| **(b) Merge into parent repo** | One repo, one CI, one PR per change, one Railway deploy hash | Larger parent repo; `frontend/` history compacts to one commit | **Chosen** |
| (c) Move to org-level repo with deploy bundle | Maximum decoupling | Maximum overhead; deploy choreography | Reject — overkill |

**Why (b) is right for now**: TransMax is one product, one team, pre-pilot. The cost of two repos exceeds the benefit of clean ownership. If we later split (e.g. open-source the frontend), we still have the bundle in `parking_lot/` to fork from with full history.

**Preserving history**: `git -C frontend bundle create ../parking_lot/frontend-pre-detangle-history.bundle --all` writes a self-contained git bundle. Anyone can `git clone parking_lot/frontend-pre-detangle-history.bundle <somewhere>` and replay the 4 commits. The squash into the parent loses commit-by-commit granularity but the bundle preserves it.

**Why squash, not replay-with-history into parent**: replaying the 4 commits onto the parent would require rewriting history with paths prefixed `frontend/` — not impossible, but adds complexity for 4 commits that are mostly the work-in-progress we're shipping anyway. The squash is the simpler tracer bullet.

**Order of operations** — must be in this order to be safe:

1. Bundle the nested repo's history (read-only — no destructive change yet)
2. Verify backend tests still green (sanity baseline)
3. `npm install` in frontend so `npm run build` is testable (deferred to AC-7)
4. Delete scratch logs
5. Update parent `.gitignore`: add `frontend/*.log`, `frontend/build_err*.log`, `frontend/build_log.txt`, `frontend/lint*.log`
6. Remove the gitlink from parent index: `git rm --cached frontend`
7. Remove nested `.git` directory: `rm -rf frontend/.git`
8. `git add frontend/` — entire frontend tree is now ordinary files in the parent
9. Run `npm install && npm run build` inside frontend; confirm green
10. Single commit + push

If step 9 fails, we **do not commit broken code** — fix or roll back the nested-repo filesystem changes (the bundle is the safety net).
