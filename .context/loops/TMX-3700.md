## 1. Task

Per plan E5 + addendum A1: pharma source documents almost always carry Word's **tracked changes** (`<w:ins>`, `<w:del>`, `<w:moveFrom>`, `<w:moveTo>`). The current `DocxIngestionService` ingests body / headers / footers / footnotes / endnotes / text boxes but **does not detect or preserve revision marks**. As a result:
- A reviewer cannot tell which segments came from a tracked insertion vs. final text
- Author and date provenance from the source doc is silently lost
- Translation of a "current draft" implicitly accepts every pending change

This loop adds revision-mark detection + author/date capture to each ingested block. The actual diff-rendering / accept-reject UX is a downstream Reviewer-Frontend concern (TMX-3702 sister); this loop carries the metadata far enough that downstream surfaces can do the right thing.

**Scope of v2**: detect whether each ingested block contains insertions or deletions, capture the unique authors and dates, attach to `block["meta"]["revisions"]`. Body text remains the FINAL text (Word's display-final-text mode) — deleted text is excluded, inserted text included.

**Blast radius**: `app/services/docx_ingestion.py` only. Block shape gains a new `meta.revisions` field; downstream consumers ignore it unless they opt in. No call-site rewiring needed.

**Addenda**: A1 (audit-by-default — preserving revision provenance is part of the audit footprint), A5 (segments carry stable IDs end-to-end — revision metadata travels with them).

## 3. Design

**Why XML-walk and not python-docx revision API**: python-docx as of 1.x has no first-class revision API. We already use `lxml` directly (see `docx_utils.py`). One traversal of the block's underlying element gathers all revision marks.

**XML namespaces** for revisions: same `w:` namespace as paragraphs. Tags: `w:ins`, `w:del`, `w:moveFrom`, `w:moveTo`. Attributes: `w:author`, `w:date`, `w:id`.

**Why store as a dict not a list of dicts**: a block can have N revision marks; for THIS loop we record presence + authors + dates. A future ticket may capture the per-mark detail (which exact text was inserted/deleted, ordered by ID). The dict shape is forward-compatible (caller can probe `meta["revisions"]` without iterating).

**Why omit the key when no revisions**: consumers shouldn't need to know about revisions to handle clean docs. Backward-compatible; reduces noise.
