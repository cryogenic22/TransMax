## 1. Task

The 2026-05-09 audit flagged **C-13** as a Critical safety hazard: `app/services/learning_service.py:85-86` auto-promotes any LLM-extracted correction with reported confidence ≥0.90 directly to `ACTIVE` status, bypassing all human review. Capabilities Spec Pillar 1 (and TransMax addendum A3) requires every active rule to carry a verifiable human signature. The current behaviour is the worst case of A3 violation: a silent fallback in a regulated path, dressed up as a "feature" ("Autonomous Update").

Addenda at play:
- **A1** — every state change emits an audit event before any side effect; the new `promote_rule()` must `log_event(RULE_PROMOTED)` BEFORE the SQL update, not after.
- **A3** — no silent fallbacks in regulated paths; auto-promote is THE canonical example of this. Killing it is non-negotiable.
- **A6** — LLM provenance: the rule's `origin_event_id` already records the segment; in a follow-up (TMX-3045b) we should also capture the model/prompt-version of the LLM that proposed the rule. Out of scope for this loop.

## 2. Spec — acceptance criteria

- [ ] **AC-1** (canonical regression for C-13): When `LearningService.process_learning_event` extracts a rule at `confidence >= 0.90`, the persisted `TranslationRule.status` is `"PROPOSED"` (NOT `"ACTIVE"`). Verified by a new test in `tests/test_rule_promotion.py`.
- [ ] **AC-2**: `app/services/rule_promotion.py::promote_rule(rule_id, approver_id, reason, *, db)` exists, takes a kw-only `db` Session, and sets `status="ACTIVE"`, `approved_by=approver_id`, `approved_at=datetime.now(timezone.utc)`, `approval_reason=reason` on the target rule.
- [ ] **AC-3**: `promote_rule` raises `PermissionError` if the resolved approver lacks `RULE_APPROVE` permission. Approver identity is supplied by the caller (FastAPI endpoint or test); the function checks against the role→permission map.
- [ ] **AC-4**: `promote_rule` raises `ValueError` if `reason` is empty/whitespace, or if the rule does not exist, or if the rule is already `ACTIVE` (idempotent-or-raise: we choose **raise**, because attempting to re-promote an already-active rule is a UI bug worth surfacing — a curator would not click promote twice).

## 3. Design

Approach in three layered changes:

**Layer 1 — Kill auto-promote (the actual C-13 fix).**
In `app/services/learning_service.py:80-90`:
```python
# OLD
status = "PENDING_APPROVAL"
if confidence >= 0.90:
    status = "ACTIVE"
    logger.info(...)
else:
    logger.info(...)

# NEW — Pillar 1 / A3: NO rule auto-promotes. EVER.
status = "PROPOSED"
logger.info(f"Learning: queued PROPOSED rule (confidence={confidence}); awaits signed promote_rule()")
```
Renaming `PENDING_APPROVAL` → `PROPOSED` because PROPOSED is the lifecycle term used in the v3 plan; existing rows with `PENDING_APPROVAL` are not migrated (they are read by status filters, and we keep the legacy term valid via the no-string-coupling principle: nothing constrains the column to a fixed enum).

Also add a method docstring on `process_learning_event` referencing Pillar 1 / A3.

**Layer 2 — `promote_rule` API + permission.**
New module `app/services/rule_promotion.py`:
- `promote_rule(rule_id, approver_id, approver_role, reason, *, db)` — A6/A1-compliant. The `approver_role` param lets callers pass the resolved `UserRole` from the auth layer; we then check `has_permission(approver_role, Permission.RULE_APPROVE)`. Alternative considered + rejected: looking up the user from DB inside `promote_rule` — this couples the function to a User table that doesn't exist in `models.py` and forces a DB roundtrip we don't need (the auth layer already resolved the role). Pass-the-role is cleaner.
- Audit event: emit BEFORE the SQL UPDATE, in the same SQLA transaction. If `log_event` raises, the rule is NOT promoted.
- Audit event needs an `audit_id`; rule promotion is NOT tied to a job, so it doesn't naturally have one. We create a per-rule audit trail on demand (`AuditService.create_audit_trail(job_id=None)` — but `AuditRecord.job_id` is nullable in the model). This avoids inventing a new event store while keeping the v1 chain semantics (TMX-3101 will replace it with audit_v2 later — that's a separate migration of all v1 callers, not this ticket).

**Layer 3 — Schema + RBAC.**
- Add 3 columns to `TranslationRule` model + migration. Columns are nullable so historical rows survive. Defensively idempotent migration uses `Inspector` like TMX-3011/3100.
- Add `Permission.RULE_APPROVE` enum value. Add it to ADMIN (already had `set(Permission)` so it's auto-included), PROJECT_MANAGER (existing curator-equivalent in pharma), and CURATOR (the canonical "rule curator" role). REVIEWER does NOT get it — a reviewer approving translations is different from a curator approving rules. TRANSLATOR/VIEWER don't get it.

**Alternatives considered + rejected:**
- *Keep auto-promote behind an env flag*: rejected — CLAUDE.md forbids "backwards-compat shims" for one-way changes. A safety hazard does not deserve a feature flag.
- *Auto-demote existing ACTIVE rules*: rejected — the audit invariant says we don't rewrite history; we surface that some rules are un-signed (TMX-3045a backfill).
- *Inline `promote_rule` in `learning_service.py`*: rejected — single-responsibility; learning extracts rules, promotion is a separate governance flow.

**ADR**: not warranted — this is a straightforward fix of a known C-13 in line with addendum A3.

## 6. Red team

22-item Tier-2 checklist run against the diff. Findings (key flags only):

- **#1 — Hidden state.** `AuditService.create_audit_trail(job_id=None)` creates an `AuditRecord` with NULL `job_id` for promotion events, breaking the historical 1:1 record-to-job pairing. Verified the column is already nullable in `app.models.models.AuditRecord` (line 177). Documented in the docstring of `promote_rule`. TMX-3101 will revisit when audit_v2 lands.
- **#2 — Different layer different abstraction.** `promote_rule` lives in `app/services/`, not `app/api/`. Endpoints can wrap it. Tests can call it directly. Right layer.
- **#3 — Hidden caller dependency.** No callers of `_save_rule` other than `LearningService` itself; ripgrep `\b_save_rule\b` returns one definition + one call. Safe to make kw-only.
- **#4 — Boundary tests.** Confidence boundary cases: 0.0, 0.5, 0.89, 0.899, 0.90, 0.901, 0.95, 1.0 — all parametrised, all PROPOSED. NaN deliberately not tested because the LLM's `data.get("confidence", 0.0)` defaults to 0.0 on missing key, and a malformed LLM response would fail at `data.get("rule_extracted")` first. Adding NaN coverage is bloat for this ticket — punted to TMX-3045d (LLM-output validation).
- **#7 — Silent fallback regression.** Verified: no `if confidence` branch in `learning_service.py`; status hard-coded "PROPOSED". `app/api/knowledge.py:create_rule` and `:import_rules` keep status="ACTIVE" but now stamp `approved_by=user.user_id` so the curator's KNOWLEDGE_MANAGE permission IS the Pillar 1 signature (not silent — fully traceable in DB).
- **#11 — Comment rot.** No stale TMX-XXX placeholder pointers introduced. The new docstrings reference TMX-3045/TMX-3045a/TMX-3101 explicitly with their roles.
- **#13 — Test fixture coupling.** New `session_factory` fixture composes `fresh_engine_for_db` (from `tests/conftest.py`) and adds in-place SessionLocal swaps for `app.models.database` and `app.services.db_service`. No double-stamp risk. Documented; no row-level lock added (over-engineering for the actual contention pattern — curator approvals are not high-frequency).
