## 1. Task

Land the `audit_events_v2` and `audit_anchors` table schemas per plan §6.A. Schema-only — the hashing implementation (TMX-3101), per-event timestamps wiring (TMX-3102), and verification API (TMX-3104) come in Sprint 2.

This is the foundation for the Audit Ledger v2 — a domain-separated chained-hash audit trail with daily Merkle-root anchoring to S3 Object Lock. v3.0's strongest regulatory differentiator. Closes review findings C-04 (string-concatenation hashing without domain separator) and starts the path to C-05 (per-event UTC timestamps) and F-C05 (placeholder hash in final audit event).

**Blast radius**: net-new tables, no existing data touched. No code paths read/write yet — that's TMX-3101+. The migration is purely additive.

**Addenda at play**:
- **A1 (audit-by-default)** — this IS the regulator-defensible audit trail. Every column is in service of A1.
- **A4 (don't deepen dual-model layer)** — audit_events_v2 lives in a new `app/models/audit_v2.py` distinct from the legacy `app/models/audit.py` (which TMX-3017 will eventually merge or deprecate). Two audit schemas exist concurrently: v1 (legacy) stays for backward-compat reads; v2 (new) is the canonical going forward.
- **A9 (soft-delete only)** — **deliberately NOT applied** to AuditEventV2. Audit rows are append-only by design; mixing in `SoftDeleteMixin` would create a way for a tampering actor to set `is_deleted=True` and the auto-filter would silently hide events. The `before_delete` listener is unnecessary because nothing should call delete on these rows. Documented in code.

## 3. Design

### File location

New file `app/models/audit_v2.py`. Deliberately separate from `app/models/audit.py` (legacy v1) and `app/models/models.py` (legacy queue-based audit). v2 is the canonical going forward; v1 reads stay for back-compat / forensics until TMX-3109 migration ships.

### Storage types per dialect

| Plan column | SQLAlchemy type | Postgres | SQLite |
|---|---|---|---|
| `*_hash` (BYTEA) | `LargeBinary(32)` | `BYTEA` | `BLOB` |
| `payload` (JSONB) | `JSON` | `JSONB`-compatible (use `JSON`; pgvector image already accepts it) | `JSON` |
| `event_ts_utc` (TIMESTAMPTZ) | `DateTime(timezone=True)` | `TIMESTAMPTZ` | `DATETIME` |
| `*_id` (UUID) | `GUID` (the TMX-3010 portable type) | `UUID` | `CHAR(36)` |
| `tsa_token` (BYTEA, nullable) | `LargeBinary` | `BYTEA` | `BLOB` |
| `anchor_date` (DATE) | `Date` | `DATE` | `DATE` |
| `s3_object_uri/version_id` (TEXT) | `String` | `TEXT` | `TEXT` |

The `LargeBinary(32)` types render as `BYTEA` on Postgres and `BLOB(32)` on SQLite. The CHECK constraints on `length(event_hash) = 32` translate cleanly on both dialects.

### Why not include `SoftDeleteMixin`

Audit events are append-only by regulatory design. If they inherited the mixin:
1. The auto-filter would silently exclude events marked `is_deleted=True` — a regulator-facing tampering vector.
2. The `before_delete` listener is redundant because nothing should call delete on these rows.
3. The chained-hash invariant means deleting any event breaks every subsequent event's hash, so the data structure itself enforces append-only.

This is the **first** non-soft-delete table in the tenant-scoped set. Documented inline.

### Genesis row semantics

Per plan §6.A: `sequence_index = 0` is genesis with `previous_hash = 32 zero bytes`. No hardcoded `GENESIS_HASH` constant — closes C-04 properly. The CHECK `length(previous_hash) = 32` accepts the all-zero bytes for genesis. Documented in the class docstring.

### `tenant_id` text column on legacy AuditRecord stays

The legacy `app/models/audit.py:AuditRecord.tenant_id` (free-text, deprecated) is unaffected. TMX-3017 will rationalise.

## 6. Red team

Walked the Tier 2 22-item checklist + A1-A10 against the diff.

**Findings I deliberated:**

1. **`SoftDeleteMixin` exclusion** is a deliberate divergence from every other tenant-scoped table. Worth special call-out:
   - Test `test_audit_events_v2_does_not_inherit_soft_delete` is the regression guard.
   - Inline class docstring explains the two reasons (auto-filter tampering vector + chained-hash invariant makes deletion meaningless).
   - **Future-loop guard** (added below for TMX-3017): when the rationalisation merges audit tables, do not blanket-apply the mixin to v2.

2. **Migration FK to `translation_jobs` is conditional**. If `translation_jobs` doesn't exist in the DB (the C-06 incomplete-mega-migration scenario), the migration drops the FK but keeps the column NOT NULL. **Trade-off**: events can be inserted with a `job_id` that references nothing on a partially-migrated DB. **Acceptable** for this ticket because:
   - The TMX-3010 init_db sweep DOES create translation_jobs on a fresh DB
   - On Postgres CI, translation_jobs exists (created via init_db in the CI step I added at `9d3c4e7`)
   - TMX-3017 closes the asymmetry by completing the alembic story
   **Tracked** for TMX-3017.

3. **`tsa_token` is `LargeBinary` without max length**. RFC 3161 timestamp tokens are typically ~1-3 KB. SQLAlchemy's `LargeBinary` without length maps to `BYTEA` (Postgres) / `BLOB` (SQLite) which have effectively no practical cap. **Fine as-is**.

4. **Genesis row semantics**. `previous_hash = b'\x00' * 32` for sequence_index=0. The CHECK `length(previous_hash) = 32` accepts this (32 zero bytes IS 32 bytes). The all-zero pattern is detectable but not collision-able with any real prior hash. Closes C-04 properly. **Verified** in round-trip test.

5. **No model-level Python defaults for `payload_hash` / `previous_hash` / `event_hash`**. Caller must compute and provide. This forces TMX-3101 (the writer) to do the canonical-bytes computation explicitly — no silent fallback to a placeholder. **Aligned with A3**.

6. **`actor_id` is nullable**. Plan §6.A allows this for system-actor events that don't tie to a user. The migration matches. **Acceptable**.

**Tier 2 22-item checklist**: clean. The diff is a textbook "deep module" — `audit_v2.py` exposes two simple data classes, all complexity (hashing, anchoring, verification) is pushed to subsequent ticket loops.
