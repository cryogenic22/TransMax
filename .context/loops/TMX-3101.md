## 3. Design — the canonical algorithm spec (load-bearing)

### Constants

```
DOMAIN_TAG    = b"transmax.audit.v1\0"   # 20 bytes; NUL-terminator is
                                          # part of the tag (domain
                                          # separator vs. any future tag
                                          # without trailing NUL)
GENESIS_HASH  = b"\x00" * 32              # exactly 32 bytes, well-defined
                                          # sentinel; NOT v1's "GENESIS_HASH"
                                          # string. Closes C-04.
```

### Canonical JSON

```
canonical_json(payload: dict) -> bytes:
  return json.dumps(
      payload,
      sort_keys=True,           # deterministic key order
      separators=(',', ':'),    # no whitespace
      ensure_ascii=False,       # preserve unicode codepoints
      allow_nan=False,          # reject NaN/Infinity (cross-language hazard)
  ).encode('utf-8')
```

**Pinned choices**:
- `sort_keys=True` — deterministic key ordering across writers/verifiers.
- `separators=(',', ':')` — no whitespace; minimises ambiguity.
- `ensure_ascii=False` — emit raw UTF-8 codepoints (e.g. `é` not `é`).
  We MUST commit to one or the other; we choose UTF-8 because it survives
  any UTF-8-aware decoder and matches modern JSON tooling (RFC 8259).
- `allow_nan=False` — Python's default emits `NaN` / `Infinity` which are
  NOT valid JSON; cross-language verifiers (e.g. a Java verifier) would
  reject them or interpret them differently. Reject at the writer.
- **Floats**: Python's `json.dumps` uses `repr(float)` which is the shortest
  round-trippable form for IEEE 754. Different language runtimes may
  emit different reprs (e.g. `1.0` vs `1` in JS). Pinned behaviour:
  payloads SHOULD use strings or ints for numerics where byte-exactness
  matters. Floats are accepted but their canonical form is "whatever
  Python 3.13 `json.dumps` produces". Documented in the writer docstring.
- **Unicode normalisation**: NOT applied. The byte sequence the caller
  passed is the byte sequence we hash. NFC/NFKC are NOT pre-applied.
  Rationale: deterministic — `"é"` (U+00E9, 1 codepoint) and `"é"`
  (U+0065 U+0301, 2 codepoints) hash differently. Callers who want
  normalised input must NFC-normalise before passing.
- **Empty payload**: `{}` is valid; canonical_json emits `b"{}"` (2 bytes).
- **Nested dicts**: recursive sort_keys; no special handling.

### Hash construction

```
def compute_payload_hash(payload: dict) -> bytes:
    return hashlib.sha256(canonical_json(payload)).digest()  # 32 bytes


def compute_event_hash(seq: int, prev_hash: bytes, payload_hash: bytes) -> bytes:
    if len(prev_hash) != 32:
        raise ValueError(...)
    if len(payload_hash) != 32:
        raise ValueError(...)
    if seq < 0:
        raise ValueError(...)
    h = hashlib.sha256()
    h.update(DOMAIN_TAG)                              # 20 bytes
    h.update(seq.to_bytes(8, 'little', signed=False)) # 8 bytes
    h.update(prev_hash)                               # 32 bytes
    h.update(payload_hash)                            # 32 bytes
    return h.digest()                                 # 32 bytes
```

Total preimage = 20 + 8 + 32 + 32 = **92 bytes** of fixed-width input. No
length-prefix needed because every component is fixed-width (and the JSON
payload is hashed first into a fixed-width 32-byte digest, which is
length-extension-resistant under SHA-256).

### Why `seq` is little-endian

Python's `int.to_bytes(8, 'little')` is the simplest cross-language
specification. Big-endian works equally well in principle — the choice is
arbitrary but MUST be pinned. We pin **little-endian** because:
- Modern x86/ARM hosts are LE; no endianness conversion overhead.
- SHA-256 itself is byte-stream-oriented; endianness is purely about how
  we serialise the integer.

Documented in the writer docstring as part of the canonical spec.

### Why `payload_hash` is its own SHA-256, not the raw bytes

The raw canonical-JSON bytes are variable-length. Hashing them first into
a fixed 32-byte digest:
1. makes the preimage to `compute_event_hash` fixed-width (92 bytes);
2. avoids any length-extension or length-prefix concerns;
3. domain-separates the payload from the chain (a verifier can recompute
   `payload_hash` independently from `event_hash`).

### Genesis sentinel

`previous_hash = b"\x00" * 32` for `sequence_index == 0`. NOT the v1 string
`"GENESIS_HASH"`. The 32-byte zero sequence:
- is detectable (any verifier can recognise it as the genesis sentinel);
- domain-separates from any real SHA-256 output (the probability of a real
  event hashing to all-zeros is 2^-256, i.e. cryptographically impossible);
- closes C-04 properly.

### Concurrency choice

For the `(job_id, sequence_index)` UNIQUE constraint: two concurrent writers
for the same job CAN collide on `seq=N`. Strategies considered:

| Option | How | Pros | Cons |
|---|---|---|---|
| (A) `SELECT ... FOR UPDATE` per-job lock | acquire row-level lock on max-seq event before computing hash | strong correctness guarantee | Postgres-only; SQLite (test env) doesn't honour `FOR UPDATE` |
| (B) Per-job advisory lock (Postgres `pg_advisory_xact_lock`) | hash job_id to int, take advisory lock | Postgres-only-good; serialises writers per-job without table-locking | doesn't work on SQLite |
| (C) **`BEGIN IMMEDIATE` + retry on `IntegrityError`** | write inside a transaction; on UNIQUE collision, re-read max+1, recompute hash, retry up to N=5 attempts | works on SQLite + Postgres uniformly; pilot-load level (sequential events per job) means collisions are rare | retry adds latency on collision; not a strict ordering guarantee |

**Chosen: (C)**. Rationale:
- Pilot load is one job at a time, sequential events. Collisions are
  vanishingly rare in production; the retry path is for correctness under
  edge cases (e.g. parallel test runners, agent + user editing same job).
- Works on both dialects (SQLite for tests, Postgres for prod). No
  dialect-specific code in the writer.
- Retry budget N=5 is generous — even under heavy contention, 5 retries
  with an arithmetic re-read-max is sufficient for any realistic concurrent
  count. Beyond 5, something is structurally wrong; raise.
- For genuinely high-concurrency per-job scenarios (a pod of agents writing
  in parallel), TMX-3101a (spawned) will add option (B) — Postgres advisory
  lock — gated by a deployment-target check.

**Findings I deliberated**:

1. **Should `domain_tag` be a column with the literal `b"transmax.audit.v1\0"`,
   or just `"transmax.audit.v1"`?** — The schema column is a `String`
   (not `LargeBinary`), so I store the decoded form (`"transmax.audit.v1"`)
   for queryability. The hash always uses the byte-form `DOMAIN_TAG`
   constant, so the column is descriptive metadata, not the algorithm
   input. The algorithm spec explicitly says `b"transmax.audit.v1\0"` is
   the hash input. Documented in writer.

2. **`session.expunge(event)` vs returning detached instance**: I expunge
   so the caller can use `event.event_hash`, `event.sequence_index`, etc.
   without holding an open session. Detached state is safe for read-only
   inspection.

3. **Why N=5 retries**: Even under heavy contention (e.g. 4 parallel
   writers for one job), 5 retries is sufficient — each retry re-reads
   max+1 so the seq advances monotonically. Beyond 5, something is
   structurally wrong (cluster-level partition, schema corruption);
   raise rather than spin forever.

4. **Float byte-exactness**: Documented as a known cross-language
   hazard. Python emits `repr(float)`; other languages may differ.
   Callers who need byte-exactness should use strings or ints. NOT a bug
   — a pinned design choice with a clear caller contract.
