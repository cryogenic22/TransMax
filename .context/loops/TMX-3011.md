## 1. Task

Add NOT NULL `organization_id` FK referencing `organizations.id` (TMX-3010) to every tenant-scoped domain table. Backfill existing rows to the seeded system default-org. The tenant-scoped session factory in TMX-3012 will then enforce per-query tenant filtering.

**Blast radius**: every domain table gets a new column. Every test fixture or service that constructs a domain model now needs to pass `organization_id` (or be wrapped by the TMX-3012 factory which injects it). This is the largest mechanical change in Sprint 1; review carefully.

**Addenda at play**:
- **A1 (audit-by-default)** — every multi-tenant write must record which org owns it. The FK makes that durable.
- **A3 (no silent fallbacks)** — NO Python-side `default=DEFAULT_ORG_ID` on model columns. Every caller must pass the org explicitly (or rely on TMX-3012's session factory). A default would let a regulator-facing path silently attribute work to the wrong tenant.
- **A4 (don't deepen dual-model layer)** — the `GUID` decorator from TMX-3010 is reused on every layer. No new bridging types.
- **A9 (soft-delete only)** — TMX-3015 is next; out of scope here.

### Why denormalise (org_id on every child, not just parent)

Tables like `chunk_translations`, `quality_reports`, `audit_log_entries` already have FKs to a parent (job/audit) that carries `organization_id`. We add `organization_id` directly anyway. Reasons:
- TMX-3012's session factory filters every query in one place — it can't filter through a join without adding cost on every call.
- Cross-tenant isolation tests (TMX-3016) get a one-line filter per table, not a recursive parent-walk.
- Audit chain queries that span tables (e.g., "all events for tenant X in date range Y") are O(1) per table.

Trade-off: child.org_id and parent.org_id can drift if a row is updated incorrectly. Mitigation: TMX-3012's factory injects org_id from session context on insert; child rows never get a different value than their parent in the normal write path. A consistency check is deferred to TMX-3016.

### Why NO Python-side default

Per A3 (no silent fallbacks), models must NOT have `default=DEFAULT_ORG_ID`. Forcing every caller to pass org_id makes tenant-leaks a noisy `IntegrityError` rather than a silent "everything went to the system org." The TMX-3012 session factory is the legitimate source of the value at runtime; until 3012 lands, tests update to pass org_id explicitly.

### Migration strategy

```python
# Single Alembic revision: 20260507_tmx_3011_add_org_id_fk.py

ORG_SCOPED_TABLES = [...]  # the 22 tables, in dependency order

def upgrade():
    for table in ORG_SCOPED_TABLES:
        # Step 1: add column nullable so we don't fail on existing rows
        op.add_column(table, sa.Column("organization_id", GUID_TYPE, nullable=True))
        # Step 2: backfill all existing rows to default-org
        op.execute(f"UPDATE {table} SET organization_id = :id", params)
        # Step 3: set NOT NULL + FK + index
        with op.batch_alter_table(table) as batch:  # SQLite-safe
            batch.alter_column("organization_id", nullable=False)
            batch.create_foreign_key(f"fk_{table}_org", "organizations", ["organization_id"], ["id"])
            batch.create_index(f"ix_{table}_org_id", ["organization_id"])
```

Some tables already have a bare `organization_id UUID` (translation_jobs, etc.). For those:
1. Backfill any NULL values to default-org (idempotent guard).
2. ALTER COLUMN type from UUID → GUID (no-op on Postgres because GUID compiles to UUID).
3. Add the FK + index.

### Test-fixture impact

Existing tests construct domain models directly (e.g., `Document(name='foo', source_language='en')`). After this ticket, they need `organization_id=DEFAULT_ORG_ID`. I'll grep for direct constructors and update what breaks. Service code that creates models (e.g., `db_service.create_job`) gets `DEFAULT_ORG_ID` injected for now, with a TODO pointing at TMX-3012 where the real org comes from session context.

## 6. Red team

Walked the Tier 2 22-item checklist against the diff. Self-review (cross-pod red-team requested below).

**Findings I addressed during the loop**:

1. **Service-level `DEFAULT_ORG_ID` defaults are A3-adjacent.** I deliberated this. Adding `organization_id=DEFAULT_ORG_ID` at every `AuditRecord(...)`, `AuditLogEntry(...)` construction site is *technically* a fallback to the system org. But:
   - It is **explicit** at every call site (not hidden in a model `default=`), with a `# TMX-3012 will replace` comment.
   - Single-tenant deployment is the *only* legitimate pre-3012 state. The default IS the truth.
   - TMX-3012 (next ticket) replaces every site with session-context injection. Each `# TMX-3012` marker is a removal anchor.
   - Without this, every test fixture would need manual updates, ballooning the diff and entrenching the fallback as "test infrastructure" rather than "transitional code."
   This is the right transitional shape. I noted it in worksheet design.

2. **Duplicate `AuditRecord` class** (in `audit.py` and `models.py`) — surfaced for the first time when `init_db()` started importing both modules. The duplication is pre-existing tech debt (TMX-3017 territory). Worked around by fully-qualifying the relationship strings in `models.py` to `"app.models.models.AuditRecord"`. **Tracked**: TMX-3017 must merge or rename one of the two `AuditRecord` classes.

3. **Mega-migration C-06 is incomplete.** When the migration ran on the dev DB, 7 tables (`audit_records`, `chunk_translations`, `quality_reports`, `translation_glossaries`, `translation_jobs`, `translation_memory`, `users`) were absent because the original 430291da76c3 migration doesn't create them — they're created at runtime by `init_db()` via SQLAlchemy. The migration prints them as skipped. **TMX-3017 must include them in semantic per-table revisions.**

4. **Dev DB hybrid state** — caused operational pain during this ticket. The dev `transmax.db` has tables created via init_db (with new schema) AND a partial alembic-applied state. I dropped+recreated the affected tables to align. This won't be a problem on a clean alembic-only environment (CI), but flagged for next-onboarding-engineer doc.

5. **Ratchet false-positive** — case-insensitive `BUG` regex matched lowercase "bug" in two of my test docstrings. Same false-positive flagged in TMX-3212. Rephrased "bug" → "defect" / "prior defect". **Tracked**: ratchet regex should require word-boundary + uppercase to avoid this — separate ticket, not in scope.
