## 1. Task

TMX-3700 (`b043075`) captured DOCX revision marks per ingested block:
```
{
    has_insertions: bool,
    has_deletions: bool,
    has_moves: bool,         # ← lumps moveFrom + moveTo together
    authors: [...],
    dates: [...],
}
```

`<w:moveFrom>` marks a position where text WAS before the author moved it elsewhere; `<w:moveTo>` marks where text ARRIVED FROM elsewhere. They come in pairs across the document but each block only sees one side. Lumping them loses the directional semantic — a reviewer can't tell whether a flagged segment lost text or gained it.

This loop adds two new boolean keys (`has_moves_from`, `has_moves_to`) and keeps `has_moves` as the OR of both for backward compatibility with the existing `<RevisionIndicator>` frontend (TMX-3702-v1) and any other consumer.

**Addenda**: A1 (audit-by-default — directional move semantics belong in the audit chain), A5 (segments carry stable IDs end-to-end — the metadata travels with them, not re-derived).

## 3. Design

The existing code:
```python
elif tag in (MOVE_FROM_NS, MOVE_TO_NS):
    has_move = True
```

becomes:
```python
elif tag == MOVE_FROM_NS:
    has_move_from = True
elif tag == MOVE_TO_NS:
    has_move_to = True
```

Then in the return dict:
```python
"has_moves_from": has_move_from,
"has_moves_to":   has_move_to,
"has_moves":      has_move_from or has_move_to,  # backward compat
```

This is the smallest change that adds the directional info without breaking any consumer.

**Why retain `has_moves`**: the frontend `<RevisionIndicator>` reads it (TMX-3702-v1 `a48c2b6`). Removing it would force a frontend lockstep change. Keeping it as derived keeps both layers honest with zero coordination cost.

**Alternatives rejected**:
- Replace `has_moves` with `has_moves_from`+`has_moves_to`, lockstep frontend update: more cross-pod coordination for marginal gain. Tracked as TMX-3704-cleanup if we ever decide to slim the wire format.
- Pair-based shape (`moves: [{id, direction, author, date}, ...]`): the existing `_collect_revisions` doesn't have per-mark detail; a richer shape would require refactoring the whole helper. Tracked as TMX-3704-detail.
