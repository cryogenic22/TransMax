  if n == 0:        merkle_root = b"\x00" * 32
  if n == 1:        merkle_root = SHA-256(b"\x01" || h_0)
  if n >= 2:
      leaves = [SHA-256(b"\x01" || h_i) for h_i in event_hashes]

      while len(level) > 1:
          next_level = []
          for i in range(0, len(level), 2):

## 3. Design — the canonical Merkle algorithm spec (load-bearing)

### Constants

```
LEAF_PREFIX     = b"\x01"          # domain separator for leaves
INTERNAL_PREFIX = b"\x02"          # domain separator for internal nodes
EMPTY_ROOT      = b"\x00" * 32     # 32-byte zero sentinel; legitimate
                                    # for orgs with no activity that day
ALGORITHM_ID    = "transmax.merkle.v1"
```

### Why two domain prefixes?

Without leaf-vs-internal domain separation, a 32-byte ``event_hash``
could collide with the SHA-256 of a tampered internal node. With
``0x01`` and ``0x02`` prefixes, any preimage-attack on a leaf cannot
substitute for an internal node, because the prefix bytes differ.
Standard Merkle-tree second-preimage hardening; matches RFC 6962
(Certificate Transparency) and similar deployments.

### Why ``0x00`` as empty-root sentinel?

The probability of a real Merkle tree producing all-zero output is
2^-256 — cryptographically impossible. Using ``b"\x00" * 32`` as the
empty-day sentinel:
- is detectable (verifier reads ``event_count=0`` and confirms root
  is zeros);
- domain-separates from any real anchor output;
- matches TMX-3101's genesis-hash pattern (consistency).

### Why duplicate-last on odd levels?

Standard Bitcoin / RFC 6962 / many production Merkle trees do this.
Alternatives considered + rejected:

| Option | How | Pros | Cons |
|---|---|---|---|
| (A) Pad with empty hash | append a fixed sentinel until level is power-of-2 | symmetric tree | requires pinning the sentinel; another constant to spec |
| (B) **Duplicate last node** | ``right = left`` when odd | simple; no sentinel | well-known Bitcoin CVE-2012-2459 (block hash duplication) — NOT applicable here because ``event_count`` is in the manifest and a duplicated leaf won't be silently appended |
| (C) Asymmetric tree | left-skewed | no duplication | non-standard; harder for an independent verifier |

**Chosen: (B)**. Rationale:
- Most widely-implemented; an independent verifier in any language has
  reference implementations to crib from.
- The CVE-2012-2459 attack (force-feeding duplicate leaves) doesn't
  apply because (a) ``event_count`` in the manifest is the authoritative
  count and (b) an attacker can't cheaply forge a chained ``event_hash``
  to land in the duplicate slot.

### Sort order (load-bearing)

```
ORDER BY event_ts_utc ASC, sequence_index ASC, event_id ASC
```

Rationale:
- ``event_ts_utc`` — primary order; user-visible.
- ``sequence_index`` — tie-breaker for events with the same wall-clock
  timestamp (rare but possible on a system that batches events).
- ``event_id`` — final tie-breaker; UUIDs sort lexicographically. No
  ties possible at this level (UUID is unique).

This is the SAME order an external verifier MUST use. Documented
verbatim in the module docstring.

### Day boundary (UTC, exclusive end)

```
[anchor_date 00:00:00 UTC, anchor_date+1 00:00:00 UTC)
```

Half-open interval. Events at exactly ``00:00:00.000`` belong to the
NEW day (anchor_date+1's anchor). Events at ``23:59:59.999`` belong
to the CURRENT day (anchor_date's anchor). Pinned in the SELECT.

**Why UTC and not local time**: UTC is unambiguous; local time would
make the anchor date dependent on the deployment's tz, and DST
boundaries would create 23-hour or 25-hour days. The audit chain is a
regulatory primitive — it must not depend on the box's clock zone.
Documented in module docstring AND red-teamed (item #4).

### Canonical manifest bytes

```python
def build_manifest(...) -> bytes:
    manifest = {
        "algorithm":      "transmax.merkle.v1",
        "anchor_date":    anchor_date.isoformat(),       # YYYY-MM-DD
        "created_at":     created_at.isoformat(),        # UTC ISO-8601
        "event_count":    len(event_hashes),
        "event_hashes":   [h.hex() for h in event_hashes],
        "first_event_id": first_event_id,                # str or None
        "last_event_id":  last_event_id,                 # str or None
        "merkle_root":    merkle_root.hex(),
        "org_id":         org_id,
    }
    return json.dumps(
        manifest,
        sort_keys=True,
        separators=(",", ":"),
        ensure_ascii=False,
        allow_nan=False,
    ).encode("utf-8")
```

Canonical-JSON flags match TMX-3101's payload canonicalisation. Keys
serialise in alphabetical order (``sort_keys=True``).

**Why ``created_at`` is part of the manifest**: it pins the wall-clock
time of the anchor build for forensic queries. Two consecutive runs
of ``build_anchor_for_day`` for the same (org, date) would produce
DIFFERENT canonical bytes because of ``created_at`` — but the second
call is refused (idempotency). So the manifest bytes are unique per
anchor.

### Signing — DEFERRED to TMX-3107b

The manifest bytes are the authoritative immutable record. Immutability
comes from S3 Object Lock retention (TMX-3107a wires the actual S3
backend + retention policy). A cryptographic signature would add a
second layer (defence-in-depth) but isn't load-bearing for the daily-
anchor invariant in this loop. Spawned as TMX-3107b.

### Concurrency / idempotency

- Two callers building anchor for same ``(org, date)`` simultaneously:
  the UNIQUE constraint catches the second. We:
  1. SELECT existing anchor before doing the upload (cheap fast-fail).
  2. INSERT — if it raises ``IntegrityError``, catch + raise ``ValueError("already anchored")``.
  This works on both SQLite + Postgres (no ``FOR UPDATE`` needed because
  the table-level UNIQUE constraint is the lock).

### Object store backend

```python
class AnchorObjectStore(Protocol):
    def put(
        self, *, key: str, manifest: bytes, root_bytes: bytes,
    ) -> tuple[str, str | None]:
        """Returns (s3_object_uri, version_id_or_None).

        Implementations MUST:
          - persist `manifest` and `root_bytes` immutably (insofar as
            the backend supports — local-fs is mutable; S3 with
            Object Lock is immutable).
          - return a uri that uniquely identifies the persisted object.
          - return a version id where the backend supports it (S3); or
            None where not (local fs).
        """
```

``LocalFilesystemObjectStore`` (default for dev/test):
- writes ``<root_dir>/<key>.manifest.json`` and ``<root_dir>/<key>.root.bin``;
- returns ``("file://<abs path>.manifest.json", None)`` as the URI.

``S3ObjectStore`` stub — TMX-3107a wires:
- boto3 client + bucket + IAM policy decisions (Programme Lead sign-off);
- ``ObjectLockMode='GOVERNANCE'`` + ``RetainUntilDate=anchor_date+7yr``;
- versioned bucket → returns ``s3_version_id``.

**Why pluggable**: mirrors TMX-3052's ``CircuitBreakerStateStore`` pattern.
Tests inject ``LocalFilesystemObjectStore``; prod injects S3.

### Schema relaxation

The fresh ``audit_anchors`` table from TMX-3100 has 4 NOT-NULL columns
that don't survive the empty-day case:

| Column | Was | Now | Reason |
|---|---|---|---|
| ``first_event_id`` | NOT NULL | nullable | empty day: no first event |
| ``last_event_id`` | NOT NULL | nullable | empty day: no last event |
| ``s3_version_id`` | NOT NULL | nullable | local-fs backend has no version id |
| ``s3_object_lock_until`` | NOT NULL | nullable | retention horizon is backend-dependent (S3 has it; local-fs doesn't) |

A new Alembic migration ``20260510_tmx_3107_relax_audit_anchors.py``
ALTERs these to nullable. Idempotent on re-runs via introspection.
Honest schema (A3): if a column genuinely can't have a value in some
legitimate state, it should be nullable, not sentinel-padded.

**Tier 2 item #4 (timezone — surfaced as red-team finding):** The
day boundary is **always** UTC. The anchor_date input is a naive
`datetime.date`; the SELECT range is built from `datetime.combine(...,
tzinfo=timezone.utc)`. If a deployment runs in non-UTC, the wall-clock
tz of the host has zero effect on which events land in which anchor.
A regulator's verifier in Tokyo and one in São Paulo MUST compute the
same anchor for `anchor_date=2026-05-10` because both build the SELECT
range in UTC. Documented in the module docstring under "Day boundary".
This is the kind of choice that bites later if not pinned upfront.

**Tier 2 #15 (locking / concurrency)**: two callers building anchor
for same `(org, date)` simultaneously:
1. Pre-check SELECT — fast-fails if the row already exists.
2. INSERT — if it raises `IntegrityError` from the UNIQUE constraint
   (race window between SELECT and INSERT), catch + raise
   `ValueError("already anchored ... (race condition)")`.

Works on both SQLite + Postgres. The race is rare in practice
(anchors are scheduled once per day per org); the IntegrityError path
is correctness-belt-and-braces.

**Tier 2 #18 (ratchet impact)**: zero new TODO/FIXME, zero new
type:ignore, zero new bare except, zero new `Any` annotations after
cleanup. Only the pre-existing TODO regression (unchanged by this
loop). Ratchet baseline holds.

**Tier 2 #11 (DRY)**: the test file's `_independent_merkle_root()`
duplicates the algorithm intentionally. If it shared code with
`AnchorBuilder.build_merkle_root`, a bug in the writer's helper would
silently propagate to the test. The duplication is a feature — it's
the spec-binding contract. (Same rationale as TMX-3101's manual
`hashlib.sha256(...)` blocks in test_independent_recompute_matches_stored.)

**Spec-binding tests (#8, #9)**: the hardcoded expected hex digest +
manifest bytes for fixed inputs are recomputed in helper functions
with NO calls into `AnchorBuilder`. If the algorithm ever drifts, both
tests fail loudly. Pinned for any future verifier (TMX-3107c) re-
implementing in another language.

**Findings I deliberated**:

1. **Should `s3_object_lock_until` be set for local-fs backend?** The
   spec doesn't define a retention horizon for local fs. I set it to
   `NULL` and relaxed the column. Alternative: `anchor_date + 7 years`
   as a cosmetic value. Rejected — A3 says don't substitute. The
   absence of retention is the truth for local fs.

2. **Why does the manifest include `created_at`?** It pins the wall-
   clock time of the build for forensic queries. Two consecutive
   `build_anchor_for_day` for the same (org, date) would produce
   different manifest bytes, but the second call is refused on the
   UNIQUE constraint — so the manifest IS unique per anchor.

3. **Why expose `event_hashes` as full hex list in the manifest?** A
   regulator's verifier needs the inputs to recompute the root. Without
   the full list, the manifest only proves *something* was hashed, not
   *what*. The list is hex-encoded (no binary in JSON) so the manifest
   is human-readable.

4. **Should the builder retry on `IntegrityError` like TMX-3101's
   writer?** No. The IntegrityError on `(org, date)` UNIQUE is the
   idempotency signal — a retry would either (a) succeed silently
   (but the prior anchor still exists; A3 violation) or (b) fail
   identically forever. Re-raising as ValueError is the right answer.

5. **Why does the builder NOT delete the upload on INSERT failure?**
   Because the upload happens BEFORE the INSERT, and the local-fs
   backend doesn't support atomic rollback. If the INSERT fails post-
   upload, we leave a manifest+root_bytes file orphaned on disk.
   Acceptable for local-fs (dev/test only); TMX-3107a's S3 backend
   will use a versioned bucket where the orphan is harmless (the URI
   is recorded only in the row that DID commit). Documented.
