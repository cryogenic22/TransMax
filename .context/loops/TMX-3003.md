## 3. Design

Two design questions: where does the validation live, and how does it fire?

**Where**: As an instance method on `Settings`, not a free function. Pydantic-settings exposes the populated fields via `self`, so the method can read every relevant field without re-importing the singleton. This is the natural Ousterhout "deep module" shape — the policy ("what is unsafe in production") is co-located with the data it inspects.

**How it fires**: Inside `get_settings()`, after `Settings()` constructs successfully but before the singleton is returned. `lru_cache` caches the result, so the validation only runs once per process. This is the exact path the audit prompt asked for.

**Alternatives considered + rejected**:
- *Free function `assert_production_safe(settings: Settings) -> None`*: would force every caller to know to call it. Putting it on the class means there's no way to forget.
- *Pydantic `@field_validator` / `@model_validator`*: would fire during construction, but the method needs to compose multiple fields and pydantic v2 model validators run before lru_cache, so the call cost is the same. Not worth the framework coupling.
- *FastAPI startup event hook*: too late — by then `from app.core.config import settings` has already completed in dozens of modules. We want to crash at first import in a misconfigured production process.
- *Separate "production hardening" module*: bloat. One module is enough for one policy.

**Placeholder list**: `""`, `"change-me-in-production"`, `"changeme"`, `"secret"`, `"placeholder"`. These are the obvious ones a developer might leave in `.env`. Not exhaustive — a determined operator can still write `"foo"` and bypass — but the goal is to catch the *defaults*, not to be a full secret-strength validator (that's vault territory, TMX-3001).

**Why an `app_env` field at all**: there is no environment-mode signal in the codebase today. Without one, the guard has nothing to key off. Defaulting to `"dev"` keeps backward compatibility; production deployments must explicitly set `APP_ENV=production` (or `staging`) — which is also the canonical signal Auth0 / vault / OTLP exporters will key off in TMX-3013 / TMX-3001 / TMX-3902.

## 6. Red team

- **CLEAN — 22/22 pass for the diff itself.**
- *Edge case considered*: what if `app_env` is something weird like `"DEV"` (uppercase) or `" dev "` (whitespace)? — The check is `app_env != "dev"`, so any non-exact match is treated as non-dev, which is the **safe** direction (a typo on `APP_ENV` fails safe rather than silently bypassing the guard). Documented in the test that `app_env="production"` is rejected; not adding case-insensitive normalisation because it would weaken the guard.
- *Edge case considered*: what if `auth_mode` is `"jwt"` but `secret_key` is the default? Caught — the secret-key check fires regardless of `auth_mode`. Important because JWT signed by a public-knowledge key is the dangerous combination.

Treated the same as production for the purposes of this guard, which means the test suite would refuse to start with the default secret_key. **Mitigation**: tests use `monkeypatch.setenv("APP_ENV", "dev")` or override the field directly. The default is `"dev"` so the only test that needs to exercise non-dev is the new `test_config_production_safety.py` itself.
