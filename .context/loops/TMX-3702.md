## 1. Task

The May 2026 review (`Transmax_Review_and_Upgrade_Path.docx`) called out a regulator-facing weakness: pharma source documents almost always carry Word's tracked changes (`<w:ins>`, `<w:del>`, `<w:moveFrom>`, `<w:moveTo>`), and the platform must surface them to reviewers — not silently translate "the current draft" as if no revisions were pending.

TMX-3700 (`b043075`) captured the revision marks at ingestion time into each ingested block's `meta.revisions = { has_insertions, has_deletions, has_moves, authors, dates }`. `app/api/documents.py:153` already persists `block.meta` into `Segment.element_meta`. Two layers — the segment-API serialiser and the reviewer surface — still need to surface the data.

This loop ships **v1**: visible indicator + author/date provenance on every segment row whose source had tracked changes. The accept/reject persistence is **TMX-3702-v2** (sister, separate loop) — v1 is a tracer bullet through the stack.

**Addenda**: A1 (audit-by-default — author attribution must be visible to a reviewer signing off on the translation), A5 (segments carry stable IDs end-to-end — revision metadata travels with them, not derived from text).

## 3. Design

**Why surface `element_meta` rather than a dedicated `revisions` field**: the JSON column already carries multiple ingestion-time facts (`section_idx`, `variant`, `revisions`, future). Exposing the column verbatim is a smaller diff than carving out a sibling field, and frontend consumers who only care about revisions can read `element_meta?.revisions`. ApiResponse stability is preserved by typing `element_meta` as `Optional[Dict[str, Any]]` — opaque from the schema's perspective; the frontend type narrows it.

**Why not parse `element_meta` server-side and emit a parsed `revisions` object**: needless transformation. The data shape from TMX-3700 is already canonical; we'd just be re-shaping for no win.

**Why ScrollText icon (lucide-react)** for the indicator: communicates "this came from a doc with edits" — a manuscript with marks. Considered Pencil (felt too "edit me"), GitBranch (suggests version control, not document tracked-changes), Edit3 (used elsewhere on the row already).

**Why one indicator per segment, not per revision**: v1 scope. Per-revision affordances arrive in v2.

**Trade-off — ts type narrowness**: I'm typing `element_meta` as `Optional[Dict[str, Any]]` server-side. Frontend narrows it. This is the canonical shape because Pydantic doesn't have a clean way to express "dict with optional revisions sub-shape" without also locking the future `section_idx`/`variant` keys. A future `SegmentMeta` Pydantic model can tighten this when the shape stops evolving (TMX-3702-meta-tighten, follow-up).

**Alternatives rejected**:
- A new top-level `revisions` field on SegmentResponse: more code, less honest about where the data lives (in element_meta).
- Eager-parse on backend: needless transformation.
- Do nothing in v1 — let v2 tackle both visible-indicator and accept/reject together: violates tracer-bullet (Pragmatic Programmer Tier 1).
