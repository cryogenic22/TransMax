## 1. Task

`app/agents/graph.py validate_request` hard-coded the JobConfigSnapshot's `system` block as `{"model": "gpt-4o", "prompts_version": "v1.0"}`. Both are placeholders: `gpt-4o` is not the configured model (`settings.default_gpt_model == "gpt-4-turbo-preview"`), and `v1.0` does not match the on-disk prompt registry version (`1.0.0`) and carries no content hash. This is a live **A6** violation (qualified-supplier telemetry: record the real model + model/prompt version) and **A8** violation (pin every prompt to a version). Fix: capture the real configured model and the registry's real per-agent `version` + `content_hash`.

Addenda at play: **A6** (LLM = qualified supplier — record real model + prompt version), **A8** (pin every prompt to a version + hash), **A3** (no silent fallbacks — registry raises rather than substituting a default), **A1** (the snapshot is an audit event; correctness of its provenance is load-bearing).

## 2. Spec — acceptance criteria

- [x] AC-1: the captured JobConfigSnapshot `config_json["system"]["model"]` equals `settings.default_gpt_model` and is NOT the literal `"gpt-4o"`.
- [x] AC-2: for each pinned agent (translator, fixer, reviewer), `system["prompts"][agent]["version"]` and `["content_hash"]` exactly match what `PromptRegistry.load(agent)` returns; `version != "v1.0"`; `content_hash` is a 64-char hex digest. The old `prompts_version` key is gone.
- [x] AC-3 (regression): the `request` block still carries `doc_id` / `target_language` / `job_id` exactly as before — the change is additive on the `system` block only.
- [x] AC-4 (consistency): the TMX-3110 v2 `CONFIG_SNAPSHOT_CAPTURED` event payload carries the SAME real model + prompt provenance as the v1 snapshot (it reuses the same dict), so the two chains do not diverge.

Out of scope:
- Capturing per-LLM-call telemetry (provider/token usage) at translate time — A6's full live-call telemetry lands with the LLM-service work, not the start-of-job snapshot. This loop fixes the snapshot's static config provenance only.
- The other graph.py known bugs (timestamp string TMX-3212/3102, `iteration_count=999` TMX-3211, `placeholder_hash` TMX-3213).
- Capturing prompt content body in the snapshot (the hash + version are the reproducibility anchor; the body is re-resolvable from the registry by version).

## 3. Design

**Approach**: add a private module helper `_build_config_snapshot(state) -> Dict[str, Any]` that returns the request block (unchanged) plus a `system` block sourcing the model from `settings.default_gpt_model` and, for each agent in `_SNAPSHOT_PROMPT_AGENTS = ("translator", "fixer", "reviewer")`, the `version` + `content_hash` from `PromptRegistry.load(agent)`. Replace the inline placeholder dict in `validate_request` with one call to the helper. The existing v2 emit at the next line already passes the same `config_snapshot` object, so it inherits the fix with zero extra edits.

**Why a structured `prompts` sub-dict keyed by agent** (vs a single `prompts_version` string): the pipeline drives three distinct LLM-backed agents, each with its own prompt and its own A8 pin. A single version string cannot represent three independently-versioned prompts. Keying by agent is the minimal shape that records each pin without inventing fields a consumer expects.

**Single source of truth (skill principle)**: the model comes from the same `settings.default_gpt_model` the pipeline uses, and the prompt provenance comes from the same `PromptRegistry` the agents load from (TMX-3200/3201). The snapshot derives from these; it does not fork a parallel copy.

**A3 (no silent fallback)**: `PromptRegistry.load` raises `PromptNotFoundError` if an agent prompt is missing. We deliberately do NOT catch it inside the helper — a missing prompt is a real misconfiguration and the snapshot must fail loud rather than record a default that lies about provenance. (The outer `try/except` in `validate_request` logs+swallows audit-init failures as it did before — that pre-existing behaviour is unchanged and out of scope.)

**Alternatives considered + rejected**:
- *Keep a single `prompts_version` string set to the translator's version* — rejected: drops fixer + reviewer provenance; still an A8 gap for two of three agents.
- *Embed full prompt bodies in the snapshot* — rejected: bloat; the `(version, content_hash)` pair is the reproducibility anchor and the body is re-resolvable from the registry by version.
- *Resolve the model per-LLM-call and store a list* — rejected: scope creep into the live-call telemetry work; the snapshot's job is the static start-of-job config.

## 6. Red team

22-item Tier 2 + A1-A10. Highlights:

- **A6** (qualified supplier): the snapshot now records the REAL configured model and real per-agent prompt versions + hashes — the core intent. Note: full live-call token/provider telemetry is a separate scope (out of scope, stated in §2); this fixes the static config provenance, which was the lie.
- **A8** (pin every prompt): each agent's prompt is pinned by semver `version` + SHA-256 `content_hash` — reproducible and verifiable.
- **A3** (no silent fallback): `PromptRegistry.load` raises on a missing prompt; the helper does NOT catch it, so the snapshot fails loud rather than recording a default.
- **A1**: the snapshot is an audit event; correctness of provenance strengthened, not weakened.
- **A4** (dual-model layers): no model/schema change; the snapshot is an opaque JSON blob (`config_json`). Untouched.
- **A5/A7/A9**: no ID re-derivation, no UI route, no delete.
- **TMX-3110 v2 consistency** (explicit red-team ask): the v2 `CONFIG_SNAPSHOT_CAPTURED` emit (graph.py ~166) passes the SAME `config_snapshot` object — verified by reading the code AND by test `test_v2_config_snapshot_event_matches_v1` which asserts the v2 payload's `system.model` matches settings and `prompts_version` is gone. The old `gpt-4o` that TMX-3110's worksheet noted would "propagate identically" is now fixed in BOTH chains in one edit. No v1 audit-path behaviour changed (regression test AC-3 + full suite green).
- **Item #4 boundaries**: empty/missing state keys — the request comprehension only picks keys present in `state`; absent keys simply don't appear (same as before). Prompt registry caches frozen records, so repeat calls are cheap and deterministic.
- **Failure mode if wrong in production**: covered in pre-mortem. Worst case is a wrong-but-plausible provenance value; mitigated by sourcing from the same SoT the pipeline uses + A3 raise-on-missing.
- **Determinism**: `content_hash` is sha256 over the YAML system+user — stable across processes; the test re-resolves via the registry rather than hard-coding a literal hash, so it won't go stale if a prompt is legitimately re-versioned.
