## 1. Task

The 2026-05-09 audit (`TRANSMAX_AUDIT_2026-05-09.md` §5) flagged C-07 as High severity:

> Circuit breaker is class-level mutable state, not thread-safe. Confirmed at `app/services/resilience.py:52-56`, with comment "Assuming single-threaded check logic or accepting race conditions for simplicity check". Recommendation: Refactor to `threading.Lock` or back with Redis (descope plan §5.3 calls for Redis).

Today's deployment (`Dockerfile:59`) runs **single-worker uvicorn** (`uvicorn app.main:app --host 0.0.0.0 --port ${PORT}`), so the multi-worker drift is latent — but the in-process race between asyncio coroutines (LangGraph nodes spawn many concurrent LLM calls) is live. Pilot scaling will move to multi-worker, at which point the cluster-drift becomes operational.

**Concurrency model.** `resilient_llm_call` is `async`. Callers come from:
- `app/agents/graph.py:336,550` — async LangGraph nodes.
- `app/services/learning_service.py:85` — async service method.
- `move_to_dlq` is sync; called from sync error-handler paths (today, no callers).

The class methods `_check_circuit`, `_record_success`, `_record_failure` are sync but read/write shared state from inside `async` methods. So the race is:
1. **Asyncio race** — even single-threaded, `await` points between the read of `cls._state` and the write let other coroutines interleave.
2. **Thread race** — if the event loop runs in a thread pool (FastAPI's default for sync handlers), or if a sync `move_to_dlq` is called from a background thread, the GIL gives no protection against compound read-modify-write on `_failure_count`.

Addenda at play: A1 (audit-by-default — the breaker's posture is a trust signal; if it lies under concurrency, regulator audit chains overstate "breaker active" status), A2 (deterministic gates — the breaker is a deterministic gate around the LLM, must be reliable), A3 (no silent fallbacks — Redis-down must fail loud, never silently fall back to in-memory; otherwise two workers diverge invisibly), A6 (LLMs are qualified suppliers — the breaker is the supplier-fault containment; if it trips wrong, the qualified-supplier promise is broken).

## 3. Design

**Choice: option (C) — instance-based `ResilienceService` with pluggable `CircuitBreakerStateStore` backend interface.**

**Alternatives considered:**

- **(A) `threading.Lock` + `asyncio.Lock` on the existing class-level state.** *Rejected*: doesn't solve the multi-worker drift the audit explicitly flagged. Descope §5.3 names Redis as the right answer. Ship-once mentality: if we know multi-worker is the pilot target, building only the in-process fix means redoing this work in TMX-3052b anyway. The marginal cost of (C) over (A) is one Protocol declaration + one stub class. Cheap.
- **(B) Pure Redis-backed shared state** (full descope §5.3 in this loop). *Rejected*: the loop spec explicitly says "DO NOT actually add Redis as a dep this loop". Rightly so — Redis adds a connection-management surface, a graceful-degradation question (which A3 forbids us from getting wrong silently), and a deployment dependency that needs review. The stub-now-wire-later split lets us land thread-safety today without a dep on Redis.
- **(D) `functools.lru_cache(maxsize=1)` factory with no backend abstraction**. *Rejected*: same reason TMX-3053 rejected it — it bakes the implementation into the call shape, makes Redis-swap a multi-file edit, and pretends the tests don't need to inject a different store.

**Why (C) is the right choice:**
1. The `CircuitBreakerStateStore` Protocol is the deepest module Ousterhout gates ask for — five small methods (`get_state`, `set_state`, `increment_failures`, `record_failure_time`, `reset`), no leaked implementation detail.
2. The `InMemoryStateStore` holds BOTH `threading.Lock` (sync callers — e.g. `move_to_dlq`) and an `asyncio.Lock` would normally be needed for async callers, BUT — every state mutation in this codebase is already a synchronous method called from inside an async coroutine. The `threading.Lock` is acquired and released synchronously inside the sync method; it never `await`s while holding the lock. So a single `threading.Lock` is sufficient. Documented in stage 6 / red team item #15.
3. The `RedisStateStore` stub fails loud (`NotImplementedError`) — A3-correct. When TMX-3052b lands, instantiating it without Redis up will raise, never fall back to `InMemoryStateStore`. (The fail-loud check belongs to TMX-3052b's actual init; the stub already raises.)
4. The factory `get_resilience_service()` mirrors TMX-3053's `get_quality_gate_service()` pattern — same `threading.Lock` + double-checked module-cache. **DRY note**: this is the second copy of this pattern. If a third lands, extract to `app.core.singletons.lazy_singleton(factory)`. Filed as TMX-LAZY-SINGLETON-HELPER for that triggering point.
5. One-way reversibility justified: the public API genuinely changes shape. Keeping the old class-level methods as deprecated shells would be a pure broken-window — they'd race in exactly the way C-07 describes, and any caller reaching for them would be wrong by definition.

**Hookable extraction.** No need — the test patches the `state_store` directly via dependency injection (`ResilienceService(state_store=mock)`).

## 6. Red team

22-item Tier 2 checklist + A1-A10 audit:

- **Item #1 (deep modules / leaky abstractions)** — `CircuitBreakerStateStore` is a Protocol with 5 methods + 2 derived getters. Implementations hide their lock detail (`InMemoryStateStore` keeps `_lock` private; the future `RedisStateStore` will hide its connection). Callers (`ResilienceService`) see only the contract. ✓
- **Item #2 (information hiding)** — `_transition_lock` is `_`-prefixed instance state; the state-store implementations encapsulate their own concurrency mechanism. ✓
- **Item #3 (different layer / different abstraction)** — yes; the Protocol is at the storage layer, the breaker is at the orchestration layer, the LLM is at the supplier layer. Each speaks its own vocabulary. ✓
- **Item #4 (boundary / RECOVERY_TIMEOUT clock skew)** — `_check_circuit` reads `time.time()` twice (outer fast path + inner under-lock recheck). If `time.time()` jumps backward (NTP correction, container freeze/thaw), `elapsed` could be negative, the breaker stays OPEN until time catches up. **Documented assumption**: monotonic-time semantics are NOT required because the worst case is "stays OPEN slightly longer", which is the safe direction (fail-closed for upstream). For TMX-3052b's Redis variant, document the same — Redis SET with EXPIRE handles it correctly. **No code change.**
- **Item #5 (single source of truth)** — yes; `state_store` is the canonical state holder. Class-level `FAILURE_THRESHOLD` and `RECOVERY_TIMEOUT` are config (read-only after construction), not state. ✓
- **Item #6 (define errors out of existence)** — `RedisStateStore.__init__` raises `NotImplementedError` rather than returning a half-functional store. A3-correct.
- **Item #7 (don't ship dead code)** — the stub `RedisStateStore` is dead today, but it's *intentional dead code* with a documented owner (TMX-3052b) and a clear contract. The alternative (delete it now, re-add when wiring) would lose the design guidance for the next loop. Acceptable.
- **Item #8 (broken windows)** — the `# TODO: Kill functionality for the job?` comment was carried over from the original code (pre-existing). Did NOT touch — out of this loop's scope. The `# FATAL: FAILED TO WRIT TO DLQ` typo (`WRIT` → `WRITE`) — pre-existing. Did NOT touch — same reason.
- **Item #9 (DRY)** — `get_resilience_service()` is a verbatim copy of TMX-3053's `get_quality_gate_service()` shape. **Findings**: the lazy-singleton pattern now exists in 2 places. Filed as **TMX-LAZY-SINGLETON-HELPER** to be triggered when a 3rd copy lands; until then, "rule of three" says it's not yet duplication worth abstracting (Hunt & Thomas). Module-level explanatory docstring cross-references TMX-3053. ✓
- **Item #10 (premature abstraction)** — the Protocol could be argued to be premature for one production impl. **Defended**: the `InMemoryStateStore` is already its own real impl (lock-protected, 7 methods); the Protocol is needed *today* for testability (3 of the 4 thread-safety tests inject a fresh store, which would not work with a class-level singleton design). The Redis path is then free. G1 5-test rubric: passes (a)/(c)/(d)/(e) clearly; (b) end-user value is indirect (regulator trust). ✓
- **Item #11 (DRY, extended)** — see #9.
- **Item #12 (locking — extra paths)** — `_check_circuit` does NOT hold the lock during `time.time()` (clock read is GIL-atomic); it acquires `_transition_lock` only for the OPEN→HALF_OPEN transition. `_record_success` holds the lock for the read-then-decide. `_record_failure` increments under the state-store's lock first, then takes `_transition_lock` for the conditional state set. **Lock-ordering**: never both held at once → no deadlock possible. ✓
- **Item #13 (every async fn cancels cleanly)** — `asyncio.wait_for(_execute_with_retry, timeout=...)` raises `asyncio.TimeoutError` cleanly; the `except Exception` handler catches it and records the failure. ✓
- **Item #14 (every state mutation paired with audit)** — A1: the breaker's tripping IS a trust signal. **Concern**: the original code only logged the trip; no audit-event was emitted. This loop preserves that behaviour (don't add scope creep). **Filed as TMX-3052c** for a follow-up: emit `AUDIT_EVENT_TYPE.CIRCUIT_BREAKER_TRIPPED` on every CLOSED→OPEN transition so the regulator-facing audit chain can prove the breaker engaged when it did. Out of scope this loop; tracked.
- **Item #15 (locking — any other shared state? must hold BOTH `threading.Lock` AND `asyncio.Lock`?)** — Analysis: every state mutation method on `InMemoryStateStore` is *synchronous*. They are invoked from inside `async` methods on `ResilienceService`, but those async methods do not `await` while holding the state-store lock. Within a single thread's event loop, a sync method runs to completion (no coroutine interleaving possible). Across threads, the `threading.Lock` serialises. **No `asyncio.Lock` needed.** This is the deliberate design: keep critical sections short and synchronous; never hold a lock across an `await`. ✓
- **Item #16 (test reliability)** — 50/50 stress passes. The tests use `Barrier(N)` (deterministic synchronisation) + `time.sleep(0.001)` (widens race window). Match TMX-3053's pattern. ✓
- **Item #17 (no silent error swallowing)** — `move_to_dlq` has `except Exception as e: logger.critical(...); session.rollback()` — pre-existing. The error is logged at CRITICAL but not re-raised; this is intentional because `move_to_dlq` is the last-resort error path. Documented in original code comments. Not touched.
- **Item #18 (boundary inputs)** — `state_store=None` → defaults to `InMemoryStateStore()`. `FAILURE_THRESHOLD=5` overridable per-instance. `RECOVERY_TIMEOUT=60` ditto. No new boundary input. ✓
- **Item #19 (test determinism)** — see #16.
- **Item #20 (configuration vs branching)** — the in-memory vs Redis choice is a future config (TMX-3052b will wire `STATE_STORE_BACKEND=redis`). Not branching in handlers. ✓
- **Item #21 (backwards-compatible API additions only)** — **VIOLATED INTENTIONALLY** (this is the `one-way` reversibility flag). The old class-level `ResilienceService.resilient_llm_call(...)` API is removed. Justification documented in worksheet header (the old API was racy by definition; deprecated shells would propagate the bug). All 5 callsites + 6 test files updated atomically in the same commit.
- **Item #22 (broken windows)** — see #8.
